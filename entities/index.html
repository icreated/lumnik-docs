    kind: Entity — fuse

    Fuse N legacy tables into one canonical, queryable thing. Each source keeps landing in its own table; the manifest says how their columns map onto one shape and which column identifies the same real-world row across systems. The hub compiles that into a SQL view — and every disagreement between sources is kept in a _conflicts ledger on the row, never silently resolved.
    Kind Entity
    Compiles to connector.v_<name> — a view; each tenant sees only its own rows
    Sources any table in the connector schema: a CSV, JDBC or Kafka connector's t_*
    Lookups optional joins[] — a table that enriches the fused rows without adding one
    Apply lm entity apply — lm_admin; validate-then-compile, atomic
    Read lm entity get NAME — lm_user, scope-bound; also lm view, lm ask
    Edition Open

    The ERP has a customer table, the CRM has another. An entity declares which one wins, exposes one row per customer, and records per row and per column where the systems disagree.

    That ledger is what a kind: View shows under Ambiguïtés et divergences, and what lm conflicts list lists across every entity you can read.

    Features

    • Join without collapsing. A lookup table enriches each fused row — one row per product with its category — and an ambiguous lookup key is shown, never guessed.
    • Priority is the source order, per column. The first source that has a value wins that column; a source that has none lets the next one fill the gap, which is never a conflict.
    • Nothing is dropped. Two distinct non-null values for one column land in the row's _conflicts ledger with the source that said each.
    • Grounding for the surfaces above. Labels a view renders, descriptions the chat reads, and a values domain the filters enforce — refusing what is outside it rather than returning an empty table.
    • Askable immediately. Applying an entity rediscovers its scopes' schema cards; the fused view is in the chat's vocabulary before the next question.
    • Refused before compiled. A manifest that cannot compile is not saved, and every refusal is a 400 that says exactly what to change.
    • The delete interlock. A connector whose table feeds an entity cannot be deleted until the entity is — a 409 that names both.

    Quickstart

    Every screen on this page reads the demo desk that ships with the repo

    Two customer exports that disagree and an order book, under docs/apps/demo/. Three commands land them; the hand count of what the fusion must give is on The demo desk.

    # 10-customer.yaml — one Customer fused from the ERP and the CRM on the customer code.
#
# The ERP is listed first, so on a disagreement its value is the representative and the
# CRM's is kept in the row's _conflicts ledger — nothing is silently dropped. The `columns`
# block grounds the canonical shape for the surfaces above: labels a kind:View renders,
# descriptions the chat reads, and a `values` domain the filters enforce.
#
# Expect: 14 rows (12 ERP + 2 CRM-only; the CRM's blank-code row is excluded), and exactly
#         three in dispute — P-1000 (name), P-1002 (city), P-1008 (city). P-1005 is not one:
#         the ERP had no city and the CRM filled it, and a gap is not a disagreement.
kind: Entity
name: AcmeCustomer
description: "A customer, fused from the ERP export and the CRM export."
match: [code]
scopes: [desk]
columns:
  code:
    label: "Code client"
  name:
    label: "Raison sociale"
  city:
    label: "Ville"
    description: "Billing city, free text."
    example: "Lyon"
  segment:
    label: "Segment"
    description: "Commercial segment."
    values: [GOLD, SILVER, BRONZE]
  credit_limit:
    label: "Encours autorisé"
    description: "Credit limit in euros."
  email:
    label: "Email"
sources:
  - table: t_acme_desk_erp
    map:
      code: code
      name: name
      city: city
      segment: segment
      credit_limit: credit_limit
  - table: t_acme_desk_crm
    map:
      customer: code
      company: name
      town: city
      email: email

    The manifest

    Field Required Meaning
    kind yes must be Entity
    name yes a simple identifier (letters, digits, _) — becomes the view connector.v_<name>, lower-cased, and the name the chat advertises
    label no the entity's human name — a kind: View that declares no title: is headed with it, and the schema card shows it beside the view name. Without one, both fall back to name
    description no free text for humans
    match yes (≥ 1) the canonical column(s) that identify the same real-world row across sources; several make a composite key. Every source must map every match column, in the same case
    sources[] yes (≥ 1) ordered — the order is the merge priority; the first source wins a disagreement, unless the column names its own (columns.<col>.prefer)
    sources[].table yes the source's dynamic table in the connector schema, without the schema prefix (t_acme_desk_erp)
    sources[].map yes (≥ 1) source column: canonical column, per source
    joins[] no relational lookups that enrich the fused rows — see Fuse or join. Never fused, never add a row
    joins[].table yes the lookup's dynamic table in the connector schema; it must not also be a source
    joins[].from yes a canonical column of the fused entity (it may be a match column) — the value looked up
    joins[].to yes a physical column of the lookup table — the key it is matched on (it need not appear in map)
    joins[].map yes (≥ 1) lookup column: canonical column; the new canonical names must not collide with any source column, any other join, or a reserved name, and none may be a match column
    scopes no the métier scopes whose chat and views may read this entity — an entity with none is not discoverable by anyone
    columns no per-canonical-column grounding
    • Column order: every sources[].map value in source order, then every joins[].map value in declared order, then _conflicts.
    • Reserved names: _conflicts, _src, _ord, _entity_id, _resolution, _source_id, _handle, _canonical_key.
    • Case: email in one source and Email in another is refused, not split into two columns.
    • Every value reads as a string: credit_limit reads "500", not 500. A column every source holds as a date or a timestamp stays one — see Dates across sources — and one every source holds as a number stays a number, so it orders and compares as one — see Numbers across sources. Any other column is text: cast where you consume.

    The key set is closed: an unknown key such as scope: for scopes: is refused, not dropped:

    $ lm entity apply -f docs/apps/demo/entities/63-refused-unknown-key.yaml
Error: API error 400: unknown key(s) in the manifest: scope — kind:Entity honors root {apiVersion, columns, description, joins, kind, label, match, name, resolution, scopes, sources}, sources[] {map, table}, joins[] {from, map, table, to}, resolution {cascade, identity}, resolution.cascade[] {exact, id, propose}, resolution.cascade[].exact {fields, normalize}, resolution.cascade[].propose {acceptAbove, provider, reviewAbove}

    Fusion semantics

    flowchart LR
  s1[("t_acme_desk_erp<br/>P-1000 · name: Hydraulique Lyon 1000")] --> f
  s2[("t_acme_desk_crm<br/>P-1000 · company: HYDRAULIQUE LYON")] --> f
  f["fusion — union of all sources,<br/>grouped by the match column"] --> c[("v_acmecustomer<br/>P-1000 · name: Hydraulique Lyon 1000<br/>first non-null, source order")]
  f -.-> k["_conflicts<br/>name: Hydraulique Lyon 1000 ↔ HYDRAULIQUE LYON<br/>nothing silently dropped"]

    The compiled view unions every source and groups by the match column(s):

    • a source row whose match column is NULL is excluded — it cannot be matched to anything;
    • for every other column, the representative is the first non-null by source order. The choice is made per column, independently: a source that wins name has no claim on city;
    • a NULL is not an opinion: a source with no value lets the next one fill the gap, and that is never recorded as a conflict. Only two or more distinct non-null values are;
    • when sources genuinely disagree, the representative still follows source order, and all the values land in the _conflicts ledger;
    • a column may name the source that goes first for it alone — prefer: in its columns: entry. The others keep the declared order.

    Dates across sources

    The same business date does not land under the same type from every source:

    Source Lands as 1 July 2026 reads
    an Oracle DATE, a PostgreSQL timestamp (no zone) a timestamp, its wall clock read in the connection's zone, UTC without one 2026-07-01 00:00:00+00
    a PostgreSQL timestamptz, an Oracle TIMESTAMP WITH TIME ZONE a timestamp, the instant 2026-07-01 00:00:00+00
    a PostgreSQL date, a CSV column through parse-date with a date-only format a date 2026-07-01
    a CSV column left as written, a Kafka field text 01/07/2026

    The fused column follows what its sources hold:

    • every source a date → the entity's column is a date;
    • dates and timestamps mixed → a timestamp, a date being its midnight UTC. A source that only knows the day cannot contradict an hour, so the sources are compared at the day: an ERP's 2026-07-01 14:30 and a CSV's 2026-07-01 agree, a CSV's 2026-07-02 is a conflict. The timed sources among themselves still compare to the instant. The value shown is a time before a day, whatever the order of sources: a day never hides the hour beside it;
    • one source text → the column stays text, compared as written, as every other text column. The hub does not guess whether 01/07 is the first of July or the seventh of January.

    A match: column follows the same rule: an ERP's 2026-07-01 00:00 and a CSV's 2026-07-01 are one record.

    An ERP's due_at (a timestamp) fused with a partner CSV's due parsed as dd/MM/yyyy (a date), and both systems' shipped, which the CSV leaves as written:

    $ lm source schema --scope livedesk

    "order_no": "SO-1",
    "due": "2026-07-01T00:00:00Z",
    "shipped": "2026-07-03 14:30:00+00",

]

    due agrees: the ERP's midnight and the CSV's day are one instant. shipped is text, and two writings of the same day are a conflict. To type it, the CSV's table must be created again: a table the hub created keeps its column types, and a new parse-date alone changes nothing.

    1. lm entity delete liveorder — the entity holds the table;
    2. lm connector delete live-partner-orders — drops its table and data;
    3. add - parse-date: { column: shipped, formats: ["dd/MM/yyyy"] } to its cell: hooks, lm apply it, and lm connector run it;
    4. lm entity apply the entity again: shipped is now timestamp with time zone.

    Once typed, the CSV's 03/07/2026 and the ERP's 2026-07-03 14:30 agree: the same day.

    A time of day has one more trap: the zone it was written in. An ERP's 2026-08-02 23:30 with no zone lands as 23:30 UTC unless its connection declares one. The same time in a CSV parsed with zone: Europe/Paris lands as 21:30 UTC: two hours apart, a conflict on every such row:

]

    Declare where each source writes: zone: Europe/Paris under the ERP's connection, the same zone on the CSV's parse-date. Once the ERP's table is read again (the gesture), both hold the same instant:

    $ lm entity get liveorder -o json

  {
    "order_id": "1",
    "ordered_at": "2026-08-02T21:30:00Z",
    "_conflicts": "{}"
  },
  {
    "order_id": "2",
    "ordered_at": "2026-01-15T22:30:00Z",
    "_conflicts": "{}"
  }
]

    A date alone has no such trap: both sides are its midnight UTC.

    A typed column is a date everywhere the entity is read: a view filters it as a date, lm ask sees its type, an entity read and an export write it in UTC whatever zone the hub runs in. The decision is taken at apply: an entity applied before a source changed type keeps its columns until it is applied again.

    Numbers across sources

    A number lands as one when its source types it: a JDBC INTEGER or BIGINT (a bigint), a JDBC NUMERIC, DECIMAL or Oracle NUMBER (a decimal, 1000021.0000), a CSV column through parse-number (integer: true for a bigint) — when the chunk that creates the column holds a number; all empty there, it is created text. A CSV column left as written is text.

    The fused column follows what its sources hold, as for dates:

    • every source a whole number → the entity's column is a bigint;
    • one decimal among them → a numeric, written without trailing zeros: an ERP's 7.0000 and a CSV's 7 are one value — one record when it is the match: key, no conflict otherwise, and 1500.0000 reads "1500";
    • one source text → the column stays text, compared as written: "10.0" and 10 disagree.

    A number column then orders as a number — 7, 12, 100, never 100, 12, 7 — in an entity read, a View and an export, and = compares it by value: --filter amount=1500.00 finds 1500. It still reads as a string. An entity applied before its sources were typed keeps its text columns until it is applied again.

    The _conflicts ledger

    One JSON object per row, one key per disputed column, {} — never null — when everyone agrees:

    {
  "city": [
    { "src": "t_acme_desk_erp", "value": "Lyon" },
    { "src": "t_acme_desk_crm", "value": "Villeurbanne" }
  ]
}

    Where it shows:

    • on every read of the entity (lm entity get);
    • at the foot of a record's detail in a kind: View;
    • across every entity in lm conflicts list — see Aggregated conflicts.

    The chat cannot query it: "where do the ERP and the CRM disagree?" is a question for lm conflicts list, not lm ask. An lm ask answer that filtered on a disputed value names the record in a disputed block (Disputed rows).

    Fuse or join

    Two different things happen between legacy tables, and an entity keeps them apart:

    Identity fusion (match + sources[]) Relational enrichment (joins[])
    The question several systems describe the same object one object references another
    Example the ERP's customer and the CRM's customer a product and its category
    Rows merged into one per match key the primary rows are never collapsed or multiplied
    Disagreement kept in _conflicts, first source wins the column none — a lookup is not an opinion

    match: [category_id] is not enrichment: it would group every product of a category into one identity and turn their differing names into conflicts. To keep one row per product and bring the category's fields along, declare the category table as a lookup:

    kind: Entity
name: ProductWithCategory
description: One row per product, enriched with its category — a join, not a fusion.
match: [product_id]
scopes: [catalogue]
sources:
  - table: t_products
    map:
      m_product_id: product_id
      m_product_category_id: category_id
      name: product_name
joins:
  - table: t_product_categories   # the lookup: it fuses nothing and adds no row
    from: category_id             # a canonical column of the fused entity
    to: m_product_category_id     # a physical column of the lookup table
    map:
      name: category_name
      description: category_description

    The fused entity is compiled exactly as before; the lookups are joined onto it afterwards as a many-to-one LEFT JOIN. For each fused row, the lookup rows whose to column equals the row's from value (see how keys are compared) decide the outcome:

    Matching lookup rows The joined columns _conflicts
    none, or from is empty all empty (NULL) — the product is kept nothing: an absence is not an opinion
    exactly one that row's values nothing
    more than one all empty — even when the rows are identical one entry per joined column, listing every duplicate row; a row with no value shows as null ((empty) on screen)

    lm view shows lookup ambiguities under Ambiguïtés et divergences, and lm conflicts list lists them with the source conflicts.

    How join keys are compared

    A key is compared as text, except that a plain decimal number is compared by value. The rule reads the value's shape, not the column's type:

    These keys match These keys do not
    1000021 = 1000021.0 = 1000021.0000 1000021.5 ≠ 1000021.5001 (nothing is rounded)
    1.5 = 1.50 01 ≠ 1, 007 ≠ 7
    '1' = '1.0', even in a text column C1 ≠ c1
    +5, 1E7, more than 38 digits: compared as text

    Two lookup rows whose keys are the same number (5 and 5.0000) are one ambiguous key, as in the table above. The search index of a joined column follows the same rule.

    A key whose from and to are both dates or times is compared as dates:

    from and to Matches on
    one of them a date (a lookup keyed by day is a calendar) the UTC day: 2026-07-01 14:30 finds the row of 2026-07-01
    both times the instant
    text on either side the rule above, as text

    A from whose sources mix dates and times is a time, so it meets a calendar at the day. Matched at the day, a lookup whose to holds times has one key per day: two of its rows on one day are an ambiguous key, as two equal numbers are — the joined columns empty, both rows in _conflicts.

    Rules worth knowing:

    • a join is always a many-to-one left join; there is no type:;
    • joins[] is flat and reads only the fused entity's columns, so cycles cannot be declared;
    • joined columns are readable, filterable, askable and exportable like any other; the entity's scopes bound the whole entity;
    • a joined column can be indexed by a kind: SearchIndex; a lookup row that arrives later re-projects the rows holding its key;
    • on a resolution: entity, the joins are read on top of the resolved view.
    Apply refusal When
    400 from is not a column the sources produce, a joined name collides, or the lookup is also a source
    400 naming the lookup table and column to or a map key does not exist in the lookup table
    409 run the source connectors first the lookup table does not exist yet

#

apiVersion: apps.lumnik.io/v1

  name: product-catalogue
spec:
  scope: catalogue
  source:
    entity: ProductWithCategory
  columns: [product_id, product_name, category_id, category_name, category_description]
  order: [product_id]
  format:
    kind: csv
  destination:
    kind: s3
    bucket: acme-outbound
    prefix: catalogue/
    filename: products.csv
    region: eu-west-3
    access_key_env: OUTBOUND_S3_ACCESS_KEY
    secret_key_env: OUTBOUND_S3_SECRET_KEY
  mode: snapshot

    The columns: grounding block

    This is where you teach the surfaces what a column means — the input the ask guards enforce and the labels a view renders:

    Key Meaning
    label the human name — a kind: View prints it as the column header and the detail's field name, Recherche shows it on its results; the schema card shows it beside the raw name
    description the business meaning, fed to the SQL-generation prompt so the model stops guessing
    example an example value, same purpose
    values the allowed domain — a filter on any other value is refused, not run (the domain guard)
    prefer the source table that goes first for this column: each system is the reference for its own fields

    A terse question such as status SO-000004 needs an example on the identifier column, or the model abstains: nothing ties that shape to a column. Declare a synthetic one (example: SO-000001); the schema card carries only what you declare.

    The rows a question returns are sent to the configured model to phrase the answer — see Models.

    After the quickstart's manifest, the scope's card carries the labels:

  name                     text           — Raison sociale
  city                     text           — Ville

    and a filter outside the declared domain is refused wherever the entity is read:

    $ lm view -f docs/apps/demo/views/10-customers.yaml --filter segment=PLATINUM

    A grounded column must exist in the canonical shape (a typo is refused at apply), and a declared value may not be blank or carry leading or trailing whitespace — it would never exact-match and would silently zero-row:

    $ lm entity apply -f docs/apps/demo/entities/64-refused-domain-whitespace.yaml

    Each system for its own fields — prefer

    A contract system is the reference for the plan; the member portal, where members type their own move, for the address. One source order cannot say both, so the address names its source:

    sources:
  - table: t_member_gestion      # first: wins every column that names no other
    map: { member_no: member_no, plan: plan, street: street, city: city }
  - table: t_member_portail
    map: { member_no: member_no, plan: plan, street: street, city: city, email: email }
columns:
  street: { prefer: t_member_portail }
  city:   { prefer: t_member_portail }
    • The portal's street is shown; the contract system's plan still is.
    • Still first non-null: a member with no street in the portal gets the contract system's.
    • Nothing is hidden: a disagreement stays in _conflicts, the preferred source's value first.
    • Each column on its own: preferring both street and city does not tie them together. If the portal holds a street and no city, the city comes from the next source.
    • Refused at apply: a table that is not one of sources[], a source that does not map the column, a match: column.

    Refusals

    Every refusal is a 400 from apply, quoting the exact problem. The ones an integrator meets first, each pinned by a file under docs/apps/demo/entities/:

    $ lm entity apply -f docs/apps/demo/entities/60-refused-no-match-column.yaml
Error: API error 400: source 't_acme_desk_crm' does not map the match column: code
$ lm entity apply -f docs/apps/demo/entities/61-refused-case-collision.yaml
Error: API error 400: canonical column 'email' conflicts with 'Email' across sources (case-insensitive collision); use one consistent case
$ lm entity apply -f docs/apps/demo/entities/62-refused-reserved.yaml
Error: API error 400: source 't_acme_desk_erp': canonical column '_src' is reserved
$ lm entity apply -f docs/apps/demo/entities/65-refused-missing-table.yaml
Error: API error 409: source relation "connector.t_acme_desk_nowhere" does not exist — the entity fuses tables its source connectors create; run the source connectors first, then apply again

    The last one is a 409, not a 400: the manifest is fine, the world is not ready for it yet.

    Refusal Meaning Fix
    kind must be 'Entity' wrong or missing kind kind: Entity
    name must be a simple identifier (letters, digits, _) — it becomes the SQL view name v_<name> advertised to the chat: … the name flows into SQL and the chat rename
    match must declare at least one column v1 needs one match rule declare the join key
    match declares a duplicate column (case-insensitive): … the same key listed twice remove the duplicate
    sources must have at least one source / source '…' map must have at least one column an entity fuses real tables declare table + map
    source '…': canonical column '…' is reserved the name is one of the reserved names pick another canonical name
    source '…' maps duplicate canonical column (case-insensitive): … two source columns feeding one canonical column in the same source keep one
    canonical column '…' conflicts with '…' across sources (case-insensitive collision); use one consistent case email vs Email would silently become two SQL columns one consistent spelling
    source '…' does not map the match column: … every source must produce the match column, same case — else its rows could never be matched add it to that source's map
    scope must be lowercase, start with a letter, then letters/digits/_/- (max 41): … a scope is a Keycloak role name — the same rule as connector scopes, see Scopes rename the scope
    unknown key(s) in the manifest: … a key kind:Entity does not honor — scope: for scopes: the message lists what it honors
    columns references unknown canonical column '…' (known: …) grounding for a column that does not exist — almost always a typo use a canonical name
    column '…' has a blank allowed value / … has an allowed value with leading/trailing whitespace … a domain value that can never match makes the guard lie trim or remove it
    409 source relation "…" does not exist — … run the source connectors first a sources[].table no connector has created yet run the source connector, then re-apply
    400 source table …: column "…" does not exist — check the sources[].map keys … a sources[].map key the physical table does not have: a typo, or a column renamed upstream since the last apply fix the key to the column the connector creates, then re-apply

    Read API

    lm entity get NAME [--filter COLUMN=VALUE]… [--limit N] [--offset N] [-o table|json|yaml]

    lm_user. The fused rows, each with its _conflicts ledger ({} when no conflict). The name is case-insensitive; an unknown entity is a 404, an empty result prints no rows.

    Option Effect
    --filter COLUMN=VALUE exact match on a canonical column; repeatable (AND). _conflicts is not filterable
    --limit N 1..1000, default 100; a full page prints note: result hit the limit on stderr
    --offset N skip N rows, to page further

    A date column reads as its UTC instant, 2026-07-01T00:00:00.000500Z, or as its day, 2026-07-02; --filter due=2026-07-01 is equal as an instant (the day's midnight UTC), as in a view. A number column is equal by value, --filter amount=1500.00 finding 1500. Every other column is text and --filter matches it exactly; a timestamp held as text reads in UTC, 2026-07-01 00:00:00+00, whatever zone the hub runs in.

    • A scope-bound user who holds none of the entity's scopes gets 403 scope not granted (see Scopes).
    • lm refuses a filter named limit, offset or identity, a column named twice, and a filter naming no column (when the page has rows to prove it).
    • For a resolution: entity, the history behind a row is on kind: Entity — resolve.
    • From a script or another system: GET /api/entities/{name}, with ?<column>=value, ?limit=, ?offset=. Over HTTP an unknown parameter is ignored, not refused.

    Aggregated conflicts

    Where do my entities hold a source conflict or a lookup ambiguity, across every entity I may read?

    $ lm conflicts list
ENTITY        KEY     COLUMNS  SOURCES
AcmeCustomer  P-1000  name     t_acme_desk_erp,t_acme_desk_crm
AcmeCustomer  P-1002  city     t_acme_desk_erp,t_acme_desk_crm
AcmeCustomer  P-1008  city     t_acme_desk_erp,t_acme_desk_crm

    lm_user. One row per record still in dispute, by entity then match key; --limit N (default 100, up to 1000). The TUI's :conflicts page shows the full ledger under d.

    • A resolution: entity's key is the record's entity id, or <source table>:<source id> while nothing has resolved it.
    • A scope-bound user's list omits the entities they hold no scope for, without a 403.
    • An entity whose view is missing or fails when read (5-second timeout) is skipped and logged; the rest of the list still answers.
    • Over HTTP: GET /api/entities/conflicts?limit=N.

    Add a third entry to sources[] — a legacy table, a Kafka topic's t_* — mapping the match column and whatever else it knows.     Troubleshooting

    Symptom Cause Gesture
    404 on lm entity get NAME (or GET /api/entities/{name}) no entity by that name has been applied (lookup is case-insensitive, so casing is not it) check the name against what apply reported, or apply the manifest
    403 {"error":"scope not granted"} on a read you hold none of the entity's scopes ask an integrator to grant one of those scope: roles
    apply refused 409: source relation … does not exist a sources[].table does not exist yet — that source connector never ran run the source connector, then re-apply
    lm connector delete refused 409: table … feeds entity … the interlock — the entity still fuses that table lm entity delete <name> first
    a row you expected is missing from the fusion its match column is NULL in that source — excluded by construction give it a key at the source, or accept that it cannot be matched
    the wrong system's value shows source order is the priority, per column reorder sources[]; the other value is in _conflicts either way
    a number is a string ("500") every value reads as a string; the column orders as a number only when every source holds a number type the CSV column with parse-number (its table is created again, as for a date), then lm entity apply — see Numbers across sources
    ids or amounts sort as text (100 before 12) one source holds the column as text the same: every source must hold a number
    a date is a string, or two sources "disagree" on the same day one source holds the date as text (a CSV left as written) type that column with parse-date: four steps, its table is created again
    an entity is missing from lm conflicts list you hold none of its scopes, or its view is gone or fails when read check your grants, or the hub log for "compiled view missing" / "compiled view unreadable"
    entity applied fine, but chat cannot discuss it no scopes declared add scopes: and re-apply; apply rediscovers the cards for you
    403 with an empty body you do not hold the role the command requires (lm_admin for apply and delete, lm_user for reads) no lm command lists your roles: GET /api/bff/v1/me returns them under roles
