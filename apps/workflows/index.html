    kind: Workflow — declare

    The fourth rung: a declarative document lifecycle over a status column ingestion already landed — states, aliases for the spellings the source really uses, the transition graph, and a threshold past which a document that has not moved is a decision.
    Kind Workflow — apps.lumnik.io/v1
    Over one column of one table: a raw connector.t_*, or a fused connector.v_* (taxonomy only)
    Declares states with aliases, transitions, provenance: declared; optionally a business key and a dormancy threshold
    Produces a data-truth report at apply; one chunk in the scope's corpus; decision.dormant.<name> alerts and an observation tape when watched
    Commands lm workflow apply · list · get · disable · enable · rm — lm_integrator, scope-bound; one lifecycle per column
    Edition Open

    Legacy exports carry dirty statuses — En cours, encours, fini, TERMINE with a trailing space. A workflow declares what they mean, so the chat answers lifecycle questions from a declared graph instead of inventing one.

    Features

    • Dirty values resolve to declared states. Alias matching is trim and case-insensitive.
    • A data-truth report that never blocks. Apply compares the declaration with the column — undeclared values, unobserved codes, blanks — and stores the manifest either way.
    • Grounded answers. The lifecycle is one chunk in the scope's corpus.
    • Dormancy. A key and a threshold turn the declaration into a watch: a document unmoved in a non-terminal state past the threshold is a decision.dormant.* in the inbox.
    • A tape that outlives the alert. Every watched document's state, since when, and whether it alerted.
    • One column, one lifecycle. A second lifecycle on the same column is refused, naming the first.

    Quickstart

    Every screen on this page reads the demo desk that ships with the repo

    An order book whose status column carries seven spellings and one blank, under docs/apps/demo/. Land it first — The demo desk has the commands and the hand count. The screens below start on day 1.

    # 10-order-lifecycle.yaml — the lifecycle the orders' status column already has.
#
# Four declared states with aliases for the spellings the export really carries, a
# transition graph, and a dormancy threshold that turns the declaration into a watched one.
# `ANNULE` is declared and never seen; `EN LITIGE` and `Terminé` are seen and never declared.
# Apply reports both — and refuses neither: a fact about the data is not a contradiction in
# the declaration.
#
# Expect: 200, dataTruth.undeclared = EN LITIGE (2 rows) + Terminé (1), unobserved = [ANNULE],
#         nullOrBlank = 1, keyNullOrBlank = 0.
apiVersion: apps.lumnik.io/v1
kind: Workflow
metadata:
  name: acme-order-lifecycle
spec:
  scope: desk
  provenance: declared
  on:
    table: connector.t_acme_desk_orders
    column: status
    key: order_no
  dormancy:
    after: 30d
  states:
    - code: BROUILLON
      label: "Brouillon"
      initial: true
    - code: EN_COURS
      label: "En préparation"
      aliases: [en cours, encours]
    - code: TERMINE
      label: "Terminée"
      aliases: [fini]
      terminal: true
    - code: ANNULE
      label: "Annulée"
      terminal: true
  transitions:
    - { from: [BROUILLON], to: EN_COURS }
    - { from: [BROUILLON, EN_COURS], to: ANNULE }
    - { from: [EN_COURS], to: TERMINE }

    The same manifest, as the graph it declares:

    stateDiagram-v2
  direction LR
  [*] --> BROUILLON
  BROUILLON --> EN_COURS
  BROUILLON --> ANNULE
  EN_COURS --> ANNULE
  EN_COURS --> TERMINE
  TERMINE --> [*]
  ANNULE --> [*]
  note right of EN_COURS
    «En préparation»
    aliases: "en cours", "encours"
    dormancy: unmoved 30d → alert
  end note
  note right of TERMINE
    alias: "fini" — terminal
  end note
    $ lm workflow apply -f docs/apps/demo/workflows/10-order-lifecycle.yaml
{"name":"acme-order-lifecycle","scope":"desk","table":"connector.t_acme_desk_orders","column":"status","dataTruth":{"undeclared":[{"value":"EN LITIGE","rows":2},{"value":"Terminé","rows":1}],"unobserved":["ANNULE"],"nullOrBlank":1,"tableMissing":false,"keyColumnMissing":false,"keyNullOrBlank":0,"checkUnavailable":false,"unavailableReason":null}}
$ lm workflow list
NAME                  TABLE                         COLUMN  SCOPE  ENABLED
acme-order-lifecycle  connector.t_acme_desk_orders  status  desk   true

    One 200, stored and indexed, with what the declaration and the data disagree on:

    • EN LITIGE sits on two orders and nobody declared it; Terminé (with its accent) on one;
    • ANNULE is declared and no order has reached it;
    • one order has no status at all.

    EN LITIGE is deliberately not in the graph: it stays visible in the report, and the dormancy sweep still watches it.

    The manifest

    Field Required Meaning
    metadata.name yes kebab-case identifier ([a-z0-9-]+) — the name apply updates under, and the alert's decision.dormant.<name>
    spec.scope yes the métier scope the lifecycle belongs to; must be a discovered scope — below
    spec.provenance yes must be declared — the only accepted value; the chat cites it
    spec.on.table yes the table to watch — an ingest table (connector.t_<table>) or a fused entity view (connector.v_<entity>, always lower-case)
    spec.on.column yes the column whose values this taxonomy explains — whatever the source called it
    spec.on.key no (required by dormancy) the business key linking a document's successive versions
    spec.dormancy.after no (required by dormancy) the sweep threshold, [0-9]+[mhd] (30d) — requires spec.on.key, and an ingest table, not a fused view
    spec.dormancy.message no the alert's sentence, in the métier's language: {doc_key}, {state}, {state_label}, {since}, {first_observed_at}, {threshold}, {workflow}; any other {name} is refused at apply. Absent: the English default below
    spec.states[] yes (≥ 1) the declared states
    spec.transitions[] no the allowed edges of the graph

    states[] — code (required; unique, case- and trim-insensitive), label, aliases[] (the dirty spellings that resolve to this code), initial (exactly one state must set it true), terminal (a terminal state may carry no outgoing transition).

    transitions[] — from[] (one edge can fan in from several states) and to.

    An unknown key is refused, at every level:

    $ lm workflow apply -f docs/apps/demo/workflows/67-refused-unknown-key.yaml
Error: API error 400: unknown key(s) in the manifest: spec.after — kind:Workflow honors root {apiVersion, kind, metadata, spec}, metadata {name}, spec {dormancy, on, provenance, scope, states, transitions}, spec.on {column, key, table}, spec.dormancy {after, message}, states[] {aliases, code, initial, label, terminal}, transitions[] {from, to}

    The scope must exist, the table need not

    spec.scope must be a discovered scope; an unknown one is a 404, as for a process:

    $ lm workflow apply -f docs/apps/demo/workflows/65-refused-unknown-scope.yaml
Error: API error 404: no schema for scope 'dsk' — run discovery first

    The table is not checked: you may declare a lifecycle before ingesting the data. The report then says tableMissing: true.

    Names the source chose

    on.column and on.key are the names your source uses, copied as they are — a Kafka message's JSON keys become columns verbatim:

    on:
  table: connector.t_Commandes
  column: "Statut Commande"
  key: "N° Commande"

    Quote them in the YAML if they contain spaces or punctuation; the hub adds the SQL quotes.

    on.table must be a table ingestion owns — connector.t_<table>, or connector.v_<entity> — spelled the way the hub created it (a connector's target keeps your capitals, a fused view is lower case, neither contains a space). Anything else is refused, the hub's own tables included:

    $ lm workflow apply -f docs/apps/demo/workflows/66-refused-foreign-table.yaml
Error: API error 400: spec.on.table is required and must name a table in the 'connector' schema that ingestion owns (connector.t_<table>) or a fused entity view (connector.v_<entity>, always lower-case), spelled the way the hub created it (letters, digits and underscores — a space is a typo): identity.app_user

    A fused view can carry a taxonomy but not a dormancy: declare the dormancy on the ingest table the entity fuses, or drop spec.dormancy.

    One column, one lifecycle

    A different name declaring an already-declared on.table + on.column is refused, naming the holder:

    $ lm workflow apply -f docs/apps/demo/workflows/64-refused-same-column.yaml
Error: API error 400: column connector.t_acme_desk_orders.status already has a declared lifecycle: workflow 'acme-order-lifecycle' — a column has exactly one lifecycle; re-apply under the name 'acme-order-lifecycle' to update it

    apply on the same name is the update. The rule is per tenant.

    Alias semantics

    Alias and code matching is trim + case-insensitive: "TERMINE ", "fini", "En cours" all resolve. On the demo desk, day 1:

    Status as written Rows Resolves to
    En cours, encours 4 EN_COURS
    fini, TERMINE 2 TERMINE
    BROUILLON 2 BROUILLON
    EN LITIGE 2 undeclared
    Terminé 1 undeclared — an accent is not an alias anyone declared
    (empty) 1 nullOrBlank

    Contradictions in the declaration are refused:

    $ lm workflow apply -f docs/apps/demo/workflows/61-refused-alias-collision.yaml
Error: API error 400: alias 'en_cours' on state BROUILLON collides with state code
$ lm workflow apply -f docs/apps/demo/workflows/60-refused-two-initial.yaml
Error: API error 400: exactly one state must be initial: true (found 2)
$ lm workflow apply -f docs/apps/demo/workflows/62-refused-terminal-outgoing.yaml
Error: API error 400: terminal state 'TERMINE' has an outgoing transition
    • an alias that collides with a state code;
    • an alias declared on two different states;
    • not exactly one initial: true;
    • a terminal: true state with an outgoing transition.

    The data-truth report — never blocks

    apply stores the manifest first, then compares it with what the column contains. The comparison never becomes a refusal:

    Field Meaning On the demo desk (day 1)
    undeclared values in the data with no matching state or alias, each with its row count EN LITIGE ×2, Terminé ×1
    unobserved declared codes never seen in the column ANNULE
    nullOrBlank rows with no status at all 1
    tableMissing the table does not exist (yet, or any more) false
    keyColumnMissing spec.on.key names a column the table does not have — the only signal a misspelled key produces false
    keyNullOrBlank rows whose key is NULL or blank: documents the dormancy sweep skips. null = not measured 0
    checkUnavailable + unavailableReason the comparison could not run (timeout, dropped column, revoked grant); the other fields are empty, not "the data agrees". Re-apply once fixed false

    keyNullOrBlank counts presence only — a row with neither key nor status is in both counters, and a present key is not proof it is unique or stable.

    The comparison looks at the 200 most frequent distinct values: on a high-cardinality column a rare undeclared value can fall below the cut.

    What the chat answers from it

    Applying a workflow indexes it as one chunk in the manifest's scope: states, aliases, transitions, provenance. Two doors read differently:

    Door Gesture Answers about
    semantic lm chat, then :scope desk (or lm scope set desk first) the graph: transitions, states, aliases
    analytic lm ask --scope desk "…", the PWA's Chat tab the rows: a document's current status

    The semantic door, asked over HTTP (the same chat lm chat reaches):

    curl -s "$HUB/api/rag/chat" -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"question":"Pourquoi je ne peux pas clôturer la commande SO-000004 ? Quelles sont les étapes avant TERMINE ?","scope":"desk"}'

    Its answer field:

    Les étapes autorisées pour passer du statut BROUILLON sont : BROUILLON -> EN_COURS, BROUILLON -> ANNULE.
Les étapes autorisées pour passer du statut EN_COURS sont : EN_COURS -> ANNULE, EN_COURS -> TERMINE.
Aucune étape n'est autorisée pour passer directement de BROUILLON à TERMINE. […]

    Every transition it names is declared. It does not know which state SO-000004 is in — the chunk carries the graph, not the table. The analytic door does:

    $ lm ask --scope desk "Dans quel statut est la commande SO-000004 ?"
La commande SO-000004 est en statut "BROUILLON".
  data as of: 2026-10-16T08:43:46.474408Z (last completed run)

  STATUS
  BROUILLON
  1 row returned

  SQL: SELECT status FROM "connector"."t_acme_desk_orders" WHERE order_no = 'SO-000004'
LIMIT 500

    Asked "why can't I close it", the analytic door abstains: it does not read the lifecycle chunk.

    Dormancy — the memory of the breathing

    A legacy status is overwritten in place: the raw table says an order is EN_COURS, not since when. A scheduled sweep records each document's state from the moment lumnik starts watching, and alerts when one has sat unmoved, in a non-terminal state, past the declared threshold.

    • Two fields switch it on: spec.on.key (order_no — links a document's successive rows) and spec.dormancy.after (30d, any [0-9]+[mhd]).
    • The sweep runs every 15 minutes (lumnik.workflow.sweep.every, Observability).
    • The clock starts at lumnik's first sighting, not at the real stall: declare after: 14d today over orders stuck for weeks, and the earliest alert is in fourteen days.
    $ lm workflow apply -f docs/apps/demo/workflows/63-refused-dormancy-no-key.yaml
Error: API error 400: spec.dormancy requires spec.on.key (dormancy is per-document; the key links a document's versions)

    Applying it

    lm workflow apply -f docs/apps/demo/workflows/10-order-lifecycle.yaml
lm workflow list
lm workflow get acme-order-lifecycle      # the stored manifest, verbatim, comments included
lm observations list                      # the tape: what has not moved, stillest first
lm observations stats                     # per workflow: watched, dormant, median detection delay
lm inbox                                  # where decision.dormant.<name> lands

    Turn it off, or remove it:

    $ lm workflow disable acme-order-lifecycle
workflow acme-order-lifecycle enabled=false
$ lm workflow list
NAME                  TABLE                         COLUMN  SCOPE  ENABLED
acme-order-lifecycle  connector.t_acme_desk_orders  status  desk   false
$ lm workflow enable acme-order-lifecycle
workflow acme-order-lifecycle enabled=true
$ lm workflow rm acme-order-lifecycle
workflow acme-order-lifecycle deleted
$ lm workflow rm acme-order-lifecycle
Error: API error 404: unknown workflow: acme-order-lifecycle

    disable stops the sweep (no new alerts) and removes the lifecycle from chat, keeping the manifest and the tape; enable restores both. rm removes it for good, with no prompt — its tape too (lm observations stats no longer lists it). Each gesture, and every apply, is recorded in the audit trail.

    Command Role Scope-bound
    lm workflow apply, list, get, disable, enable, rm lm_integrator yes — outside your grants, 403 scope not granted; list shows only your scopes
    lm observations list, stats lm_integrator and lm_admin (or lm_superadmin) yes — they list only the workflows of your scopes

    How to…

    Declare the lifecycle a legacy status column already has

    lm workflow apply -f docs/apps/demo/workflows/10-order-lifecycle.yaml
lm workflow get acme-order-lifecycle

    Result: the manifest is stored and indexed in one 200, with the data-truth report. The semantic chat in that scope now answers transition questions from the declared graph.

    Get told when a document stops moving

    The demo manifest already carries spec.on.key and spec.dormancy.after: applying it switches the sweep on. Alerts land in lm inbox (and the PWA's Décisions tab) for users holding the workflow's scope and for users with no scope: role. To push them to an external system, lm integration add (Processes).

    Don't treat the inbox as a register of everything asleep. A document alerts once per stall, and the alert ages out with the event log (30 days by default). The tape keeps it — see Re-alert semantics.

    Add the value the report says nobody declared

    dataTruth.undeclared named EN LITIGE. Add it as a state (or an alias of one) and re-apply under the same name. Result: the report no longer lists it, the chat knows what it means, and the sweep watches it as a declared state. The documents the tape held as EN LITIGE, and the source still holds, read the declared code from the next tick; a meaning is not a movement, so their SINCE, their alert and the transition journal stay as they were.

    Checking a proposal dossier

    A business person can describe a problem on lumnik.fr and download a proposal dossier. Before turning it into manifests, ask the hub what it can establish on your data, against a workflow you already applied. No lm command does this; the door is HTTP:

    curl -X POST "$HUB/api/proposal/check?workflow=<name>" \
  -H "Authorization: Bearer $TOKEN" \
  --data-binary @dossier.md > dossier-checked.md

    It needs lm_integrator; $TOKEN is the token lm login stored (see the HTTP API quickstart). The answer is the same file, checked; nothing is applied, and the original answers are untouched. Without workflow=, the dossier is only recomputed.

    Point Confirmed when Refuted when
    a status column exists the comparison read the column the table is there and the column is not
    an identifier column exists the table has the spec.on.key column the table is there and does not have it (judged only if the status column exists)
    the target is accepted by the watch validation the workflow is stored never
    • What only a person can establish (the column describes the lifecycle, the identifier is stable) stays to be established.
    • A table not ingested yet, a timeout or a missing grant leave a point unchanged.
    • The proof is about your data today.
    • A dossier for another catalogue version is returned recomputed, unverified.
    • The answer is the same whether the workflow does not exist, is not yours, or no longer parses.
    • A malformed dossier is a 400 with the reason (duplicate-key); a file that is not UTF-8 is a 400 malformed-header.

    Drafting a manifest from a dossier

    lm proposal draft writes the start of the manifest a dossier proposes. It does not contact the hub:

    lm proposal draft dossier.md \
  --name orders-lifecycle --scope sales \
  --table connector.t_commandes --column statut --key n_commande --after 14d \
  -o orders-lifecycle.yaml
    • Every flag is optional; a value you leave out is left out of the file, with a comment saying where it goes.
    • States and transitions are never generated: you write them before lm workflow apply.
    • --after without --key is accepted here and refused at apply.
    • The header comments list each point, refuted first, then missing, unverified, confirmed; what no tool can check is marked to establish yourself.
    • -o never overwrites a file; without it the draft goes to stdout. The dossier can come from stdin (lm proposal draft -).
    • A dossier with no stalled-documents@1 lead, or two, is refused; other leads are named on stderr.

    The loop: draft → complete and lm workflow apply -f → check the dossier against the stored workflow (the curl above) → draft again from the checked dossier, to a new file.

    Advanced: the sweep in detail

    What the sweep skips, the alert's wording, re-alerts, the tape, and scale

    What the sweep does not see

    A document with a NULL or blank key, or a NULL or blank status, is skipped — permanently: there is nothing to follow it by, or no state to watch (SO-000009 on the demo desk). The apply report counts both: keyNullOrBlank and nullOrBlank.

    The alert, verbatim

    From the demo desk, with dormancy.after shortened to 1m:

    SO-000004: observed unmoved in "BROUILLON" since 2026-10-18 (first observed 2026-10-18) — declared threshold 1m in acme-order-lifecycle

    The default shape — <key>: observed unmoved in "<state>" since <date> (first observed <date>) — declared threshold <after> in <workflow> — never asserts how long the document sat in the source. It is emitted as decision.dormant.<workflow> and appears in the inbox as workflow:<workflow>.

    A workflow writes the sentence in its métier's language with spec.dormancy.message:

    dormancy:
  after: 14d
  message: "{doc_key} : immobile en « {state_label} » depuis le {since} — seuil {threshold}"

    {state_label} is the state's declared label (its code when the state is undeclared); dates are the UTC day. A placeholder outside the seven is refused at apply, naming it.

    Re-alert semantics

    A document alerts once per stall. It alerts again only after it moved (a new state resets its clock) and then sat unmoved past the threshold once more.
    A permanently stuck document alerts once; the alert leaves lm inbox with the event retention (lumnik.events.retention-days, 30 by default)
    What to do ack the alert into your own tracker, or raise lumnik.events.retention-days beyond your review cadence
    What stays the tape: lm observations list keeps ALERTED until the document moves

    Reading the tape

    lm observations list — the watched documents of every workflow in your scopes, stillest first (--limit, default 200, at most 1000). SINCE is when lumnik started observing that state; ALERTED is empty until the sweep alerts. lm observations stats sums it up per workflow. The TUI's :observations screen shows the same, with humanized ages. Both need lm_admin (or lm_superadmin) on top of lm_integrator.

    lm observations transitions reads the journal: every observed move, newest first (--workflow, --doc, --limit). IN_FROM_S is the seconds the document spent in FROM, from ENTERED — its previous move, or its first observation for its first one (a lower bound, like SINCE). Moves are seen at sweep granularity: a document that moved twice between two ticks shows one move.

    Scale

    Each tick reads the latest state of every business key, in the database. On a table with millions of distinct documents, lengthen lumnik.workflow.sweep.every. That read spills to temporary files and counts against PostgreSQL's temp_file_limit; past it, the tick logs dormancy sweep failed ….

    The tape and its transition journal are never pruned; only lm workflow rm clears them.

    A workflow whose table, status column or key column is gone is skipped, logged once: dormancy sweep standing down for tenant … workflow …; it resumes by itself, with one log line, when the table is readable again. Any other failure (timeout, revoked grant) logs dormancy sweep failed for tenant … workflow … — skipped on every tick. Other workflows are never affected.

    An undeclared value can never be terminal

    EN LITIGE is not declared, so it cannot be terminal: true: a document sitting in it is watched like any non-terminal state. The apply report names the value; the sweep names the documents asleep in it.
