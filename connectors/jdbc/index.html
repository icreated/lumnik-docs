    JDBC

    Read tables from a live PostgreSQL or Oracle database into hub tables — the whole table once, then only what changed, on a schedule.
    Type jdbc-generic
    Dialect postgres — Open; oracle — Pro only
    Target connector.t_<table>, or connector.t_<target>
    Schedulable cron
    Edition Open for PostgreSQL. Oracle ships only in lumnik Pro — see Oracle

    The connection is read-only: every query this connector issues is a SELECT.

    Quickstart — one table, three commands, a look at the ledger

    # 10-full-dump.yaml — the whole table, once, then only what is inserted after it.
#
# `mode: full` pages through the table by primary key and remembers the last key it read.
# The next run continues past that key: new rows arrive, rows changed in place do not.
# Switch this same connector to `20-watermark.yaml` to pick up changes too.
#
# The source tables are created by data/demo-source.sql in the hub's own PostgreSQL, so the
# page can be replayed with nothing but the self-host stack. LUMNIK_READONLY_DB_PASSWORD is
# already exported where the hub runs; a real base names its own variable.
apiVersion: connectors.lumnik.io/v1
kind: Connector
metadata:
  name: demo-invoices
  connector_type: jdbc-generic
  scopes: [billing]

spec:
  connection:
    url: jdbc:postgresql://postgres:5432/lumnik
    user: lumnik_readonly
    password_env: LUMNIK_READONLY_DB_PASSWORD

  defaults:
    schema: demo

  source:
    tables:
      - name: invoices
        mode: full
        pk_columns: [invoice_id]

    The screens on this page read a demo source in the hub's own PostgreSQL — four tables and a view — so they replay on the self-host stack alone. Create it first:

    docker exec -i lumnik-postgres-1 psql -U lumnik -d lumnik < docs/connectors/jdbc/data/demo-source.sql

    Two modes — full and watermark

    Both modes page through the table 500 rows at a time and remember where they stopped:

    • mode: full remembers the last primary key it read. The next run continues past it.
    • mode: watermark remembers the last value of a column that moves on every change, plus that row's key. The next run reads everything past that value.
    mode: full mode: watermark
    ordered by primary key watermark column, then primary key
    cursor holds the last primary key the last watermark value and its row's key
    a row inserted with a higher key read read
    a row inserted with a lower key (a backfill) never read read — the insert stamps the column
    a row updated in place never read again read again
    a row deleted never noticed never noticed
    a run with nothing changed 0 rows 0 rows
    declares pk_columns pk_columns and watermark_column

    The watermark manifest

    The quickstart's connector, read incrementally. mode and watermark_column sit under defaults:, which holds what every table of the connector shares:

    # 20-watermark.yaml — the same table, read incrementally on a column that moves on every change.
#
# `updated_at` only ever grows, so a run reads the rows past the persisted cursor and nothing
# else: an INSERT and an UPDATE both arrive, a run with nothing changed reads 0 rows.
#
# Same connector name as 10-full-dump.yaml on purpose. Applying this over a table that already
# ran in `full` meets the cursor the full read persisted; the hub recognises it as foreign,
# logs a WARN naming both, and restarts the table from the beginning. A row the hub table already
# holds unchanged is skipped — the table does not grow.
apiVersion: connectors.lumnik.io/v1
kind: Connector
metadata:
  name: demo-invoices
  connector_type: jdbc-generic
  scopes: [billing]

spec:
  connection:
    url: jdbc:postgresql://postgres:5432/lumnik
    user: lumnik_readonly
    password_env: LUMNIK_READONLY_DB_PASSWORD

  defaults:
    schema: demo
    mode: watermark
    watermark_column: updated_at

  source:
    tables:
      - name: invoices
        pk_columns: [invoice_id]
        indexes:
          - { columns: [customer], unique: false }

  # Uncomment to let the hub poll the source itself. Incremental runs cost one keyset query
  # per table when nothing has changed. Cron times are UTC.
  # schedule: "*/10 * * * *"
  # window: "22:00-06:00"

    Which one to declare

    • watermark, whenever the source stamps a column that moves on every write. ERPs usually have one: updated_at, updated, modified_at, last_modified.
    • full, for a table that only grows — an append-only ledger, a reference table nobody edits in place.
    • full on a table that is edited in place will not see the edits. Expose a timestamp column on the source, or re-read the table with lm endpoint reset-cursor before each run.

    A watermark column that does not move is worse than full

    The hub cannot check that the column moves. Two ways to get it wrong, both silent:

    • A column the application forgets to touch on some writes — those changes never reach the hub.
    • A numeric primary key as the watermark. lm source jdbc discover suggests one when it finds no timestamp (see price_list below) — it behaves like mode: full.

    Connection

    connection:
  url: jdbc:postgresql://db.acme.io:5432/billing   # required
  user: ro_user                                    # required
  password_env: ACME_DB_PASSWORD                   # required — a hub variable, else an lm secret
  dialect: postgres                                # optional, inferred from the url
  zone: Europe/Paris                               # optional, UTC when absent
    • Dialect: PostgreSQL (postgres, alias postgresql) ships with every edition; Oracle (oracle) only with lumnik Pro — see Oracle. A declared dialect that is not installed, or does not accept the URL, fails validation. An absent one is inferred when exactly one installed dialect accepts the URL.
    • Zone: the time zone the database writes its dates-and-times in when it stores no zone with them — see A time without a time zone. An unknown zone fails validation. A connector made by lm source jdbc add has no zone option: it reads such times as UTC.
    • Grants: USAGE on the schema and SELECT on the tables. Nothing more.
    • Reachability is the hub's, not yours. The URL is resolved where the hub runs: a database on your Mac is host.docker.internal for a hub in Docker, not localhost.

    Where the password comes from

    Resolved at run time, first match wins:

    Source Notes
    1 Attached credential Stored encrypted, created by lm source jdbc add as <source-name>--credential. lm apply never sets one.
    2 password in the manifest Plain text, dev and test only. It wins over password_env; lm validate warns.
    3 password_env The name of a variable in the hub server's environment (OS variable or JVM system property), else of an lm secret entry. Neither at run time is a failed run naming it.
    • password_env is required by validation even when password is present.
    • The hub's environment comes first, unlike REST and the file transports, which read lm secret first: a name the environment holds keeps the value it always had. A connector written as a manifest gets its password with lm secret set ACME_DB_PASSWORD, no hub restart.
    • The attached credential is encrypted under LUMNIK_CRYPTO_SECRET_KEY — see Security → Secrets at rest.

    Source — one entry per table

    # 40-two-tables.yaml — two tables under one connector, each with its own mode.
#
# Every entry in `source.tables[]` becomes an endpoint, and every endpoint gets its own run
# row in the ledger: one `lm connector run` on this connector produces two rows. `defaults:`
# carries what both tables share; each table overrides what it needs.
apiVersion: connectors.lumnik.io/v1
kind: Connector
metadata:
  name: demo-erp
  connector_type: jdbc-generic
  scopes: [billing]

spec:
  connection:
    url: jdbc:postgresql://postgres:5432/lumnik
    user: lumnik_readonly
    password_env: LUMNIK_READONLY_DB_PASSWORD

  defaults:
    schema: demo

  source:
    tables:
      - name: warehouses
        mode: watermark
        watermark_column: updated_at
        pk_columns: [warehouse_id]

      - name: price_list
        mode: full
        pk_columns: [id]
        rename:
          id: price_list_id

    Each entry in source.tables[] is an endpoint of the connector:

    • the endpoint name is the table name;
    • one lm connector run runs all of them;
    • each endpoint writes its own row in the run ledger — two rows per run here.
    $ lm run list --connector demo-erp
ID        CONNECTOR  ENDPOINT    STATUS     IN  OUT  SKIPPED  DEAD-LETTERS  STARTED           ENDED
122112a8  demo-erp   price_list  Completed  0   0    0        0             2026-10-19 01:41  2026-10-19 01:41
d2eb4159  demo-erp   warehouses  Completed  0   0    0        0             2026-10-19 01:41  2026-10-19 01:41
4013a639  demo-erp   price_list  Completed  3   3    0        0             2026-10-19 01:41  2026-10-19 01:41
664b8c9b  demo-erp   warehouses  Completed  2   2    0        0             2026-10-19 01:41  2026-10-19 01:41

    The first run read warehouses (2 rows) and price_list (3); the second found nothing new. ENDPOINT is also the second half of the endpoint commands' address: lm endpoint reset-cursor demo-erp/warehouses.

    Per-table keys

    Key Required What it does
    name yes The source table. Also names the hub table, connector.t_<name>, unless target does
    target no Names the hub table connector.t_<target> instead
    schema yes (here or in defaults) The source schema
    mode yes full or watermark
    watermark_column when mode: watermark The column that moves on every change
    pk_columns yes The paging key and the hub table's key: one row per key. It must be unique together
    indexes no Postgres indexes to create on the hub table
    rename no Source column name → hub column name
    • chunk_size is refused; any other key gets a warning, unknown key — ignored by the runtime — see Validation rules.

    pk_columns is the paging key, read whole

    The reader orders by every entry and resumes on all of them at once. A composite key pages exactly like a single-column one. demo.order_lines is 700 lines over 100 orders, seven each:

    # 60-composite-key.yaml — a table whose primary key is two columns.
#
# `pk_columns` is the paging key and it is read WHOLE: the reader orders by (order_id, line_no)
# and resumes on the pair, so no order is split by a chunk boundary. The order of the entries is
# the paging order — reverse it and the stored cursor becomes foreign, and the table restarts.
#
# What has to hold is that the key is unique TOGETHER. `order_id` alone is not: 700 lines over
# 100 orders, seven lines each. demo.order_lines is created by data/demo-source.sql.
apiVersion: connectors.lumnik.io/v1
kind: Connector
metadata:
  name: demo-lines
  connector_type: jdbc-generic
  scopes: [billing]

spec:
  connection:
    url: jdbc:postgresql://postgres:5432/lumnik
    user: lumnik_readonly
    password_env: LUMNIK_READONLY_DB_PASSWORD

  source:
    tables:
      - name: order_lines
        schema: demo
        mode: full
        pk_columns: [order_id, line_no]

    The full read, then a second run that finds nothing:

    $ lm run list --connector demo-lines --limit 2
ID        CONNECTOR   ENDPOINT     STATUS     IN   OUT  SKIPPED  DEAD-LETTERS  STARTED           ENDED
a04d56c9  demo-lines  order_lines  Completed  0    0    0        0             2026-10-19 01:42  2026-10-19 01:42
17ce005f  demo-lines  order_lines  Completed  700  700  0        0             2026-10-19 01:41  2026-10-19 01:41
note: result hit the limit of 2 — there may be more
    • The order of the entries is the paging order. Reversing it restarts the table (see What restarts a table).
    • The key must be unique together. lm source jdbc add writes the discovered primary key; a hand-written manifest may not. A run that meets two rows under one key fails, and that read writes nothing. demo.order_lines declared on order_id alone:
    $ lm run get 0fdd0a87
ID        CONNECTOR   ENDPOINT     STATUS  IN  OUT  SKIPPED  DEAD-LETTERS  STARTED           ENDED
0fdd0a87  demo-lines  order_lines  Failed  0   0    0        0             2026-10-19 01:42  2026-10-19 01:42
✖ run failed: pk_columns (order_id) does not identify one row of demo.order_lines: two rows share the key where a read ends, and paging past it would skip one — declare the columns of the source table's primary key

    defaults

    defaults: holds fallbacks for every table; a table that declares the same key wins.

    • The merge is per key, not deep: a table's rename: replaces the one in defaults:.
    • mode, watermark_column and schema are the usual ones — see the watermark manifest.

    Chunking is fixed

    Reads page through the source in 500-row chunks, keyset-paginated on pk_columns. There is no chunk_size setting: lm validate refuses one.

    The hub table

    Rows land in the connector schema as connector.t_<table-name>, one table per source table, created on the first run from the columns the source returned.

    The hub table is named after the source table, not the connector

    Two connectors of a tenant reading a table of the same name land in the same connector.t_<name>. The second one's run is refused; give it its own hub table with target: — see Two connectors reading a table of the same name.

    Column types

    The hub types each column from the source's declared type:

    Source type Hub column
    smallint, integer, bigint BIGINT
    real, double precision, numeric, decimal NUMERIC(18,4)
    timestamp (no time zone) TIMESTAMPTZ, the time read in the connection's zone, UTC without one (below)
    timestamptz TIMESTAMPTZ, the same instant
    date DATE
    boolean, bit BOOLEAN
    everything else TEXT
    • Oracle has its own list and refuses a column outside it — see Oracle.
    • NUMERIC(18,4) holds at most 14 digits before the point. A wider source column — a 19-digit id declared numeric(20,0) — fails the run with numeric field overflow. Expose it as text through a view: SELECT event_id::text AS event_id, .... A bigint id is not affected.

    • A time without a time zone is read in the connection's zone, UTC when it declares none, wherever the hub runs. A timestamptz keeps its instant. ordered_at is a timestamp at the source, paid_at a timestamptz holding the same instants — read on a hub running in Paris, no zone declared:

       order_id |       ordered_at       |        paid_at
----------+------------------------+------------------------
        1 | 2026-08-02 23:30:00+00 | 2026-08-02 23:30:00+00
        2 | 2026-01-15 23:30:00+00 | 2026-01-15 23:30:00+00

      An ERP that writes Paris time declares it: zone: Europe/Paris under connection. Each time is then read at its own offset, UTC+2 in summer, UTC+1 in winter. A date keeps its day:

       order_id |       ordered_at       |   due_on
----------+------------------------+------------
        1 | 2026-08-02 21:30:00+00 | 2026-08-02
        2 | 2026-01-15 22:30:00+00 | 2026-01-15

      The zone applies to the rows a run reads. On a table already written, re-apply the connector, then read the table again:

      $ lm apply -f erp.yaml
{"name":"erp","connectorId":"e99abc0f-33d6-4e9d-99fc-a7240007c0c1","endpointsApplied":1}
$ lm endpoint reset-cursor erp/orders
$ lm connector run erp
run scheduled: a97e7633-c3d3-43f6-8aac-a3dd0711aed7
$ lm run list
ID        CONNECTOR  ENDPOINT  STATUS     IN  OUT  SKIPPED  DEAD-LETTERS  STARTED           ENDED
a97e7633  erp        orders    Completed  2   2    0        0             2026-10-20 15:33  2026-10-20 15:33

      Each row it reads again is rewritten in place, at the right instant. Without reset-cursor, the run reads only what is new and the old rows keep their time. An unknown zone is refused before anything is written:

      $ lm apply -f erp.yaml
✗ erp.yaml — 1 error(s), 0 warning(s)

  ERROR    spec.connection.zone
          'zone' is not a time zone: "Europe/Pariss" (for example Europe/Paris or UTC)

    • A table the hub already created keeps the types it was created with. To retype it, delete the connector (which drops its tables) and re-ingest, or ALTER the columns yourself.

    Seven reserved column names

    id, _row_hash, _ingested_at, _source, _run_id, _mapping_version, tenant_id — the hub adds these to every table it creates. A source column of one of those names fails the run:

    $ lm run get ded8b2ac
ID        CONNECTOR        ENDPOINT    STATUS  IN  OUT  SKIPPED  DEAD-LETTERS  STARTED           ENDED
ded8b2ac  demo-price-list  price_list  Failed  0   0    0        0             2026-10-19 01:41  2026-10-19 01:41
✖ run failed: source column 'id' collides with a hub system column (_ingested_at, _mapping_version, _row_hash, _run_id, _source, id, tenant_id); it must reach the hub under another name — jdbc: source.tables[].rename; csv: a map-columns row hook under spec.mapping; kafka: no rename exists, the field must be renamed in the topic payload

    rename: is the fix:

    # 30-rename-reserved-column.yaml — a source table whose primary key is called `id`.
#
# The hub adds seven columns of its own to every table it creates, `id` among them, so a
# source column of that name is refused at write time rather than silently dropped. `rename:`
# is the fix: the source column lands under another name in the hub table. Nothing is renamed
# on the source — the connection stays read-only.
apiVersion: connectors.lumnik.io/v1
kind: Connector
metadata:
  name: demo-price-list
  connector_type: jdbc-generic
  scopes: [billing]

spec:
  connection:
    url: jdbc:postgresql://postgres:5432/lumnik
    user: lumnik_readonly
    password_env: LUMNIK_READONLY_DB_PASSWORD

  source:
    tables:
      - name: price_list
        schema: demo
        mode: full
        pk_columns: [id]
        rename:
          id: price_list_id

    $ lm connector run demo-price-list
run scheduled: ee29d37e-843e-4cd3-8972-9422ea54b36e
$ lm run list --connector demo-price-list
ID        CONNECTOR        ENDPOINT    STATUS     IN  OUT  SKIPPED  DEAD-LETTERS  STARTED           ENDED
ee29d37e  demo-price-list  price_list  Completed  3   3    0        0             2026-10-19 01:41  2026-10-19 01:41
ded8b2ac  demo-price-list  price_list  Failed     0   0    0        0             2026-10-19 01:41  2026-10-19 01:41

     price_list_id |   sku    |  price
---------------+----------+----------
             1 | PUMP-075 | 349.0000
             2 | HOSE-32M |  59.9000
             3 | FILT-A1  | 129.5000
    • The rename applies in the hub table only. Nothing is renamed on the source.
    • lm validate refuses a rename into one of the seven, and two source columns renamed onto the same hub column.

    One row per key — a changed row replaces its version

    The hub table holds one row per pk_columns value:

    • A row read again unchanged is skipped. It keeps its _ingested_at and _run_id.
    • A row changed at the source replaces its previous version, with a new _ingested_at and the _run_id of the run that read the change.

    After the five runs above, t_invoices holds five rows for five invoices:

     invoice_id | status |       updated_at
------------+--------+------------------------
       1001 | paid   | 2026-09-01 09:15:00+00
       1002 | paid   | 2026-09-08 07:45:00+00
       1003 | paid   | 2026-09-08 09:10:00+00
       1004 | draft  | 2026-09-02 16:20:00+00
       1005 | open   | 2026-09-08 07:30:00+00

    The hub table is the source's current state; it keeps no history. A table written by an older hub may still hold one row per version — see Upgrading.

    OUT counts rows delivered, not rows written

    Rows skipped because they did not change are counted in OUT too, which is why a re-read that changes nothing still reports a non-zero OUT.

    Deletes are never propagated

    A row deleted at the source stays in the hub table, in both modes. To resync from nothing, delete the connector, then apply and run it again.

    Emptying one endpoint on its own

    A jdbc-generic endpoint cannot be purged on its own. lm endpoint purge asks the hub first, so the refusal comes with no prompt:

    $ lm endpoint purge demo-invoices/invoices
Error: API error 400: This endpoint writes to a connector table whose rows are not tracked per endpoint, so it cannot be purged on its own. Deleting the connector removes its data, along with its run history.

    Delete the connector instead. --dry-run states what goes:

    $ lm connector delete demo-invoices --dry-run
Would delete connector demo-invoices (jdbc-generic) — 5 rows of connector.t_invoices, its run history and RAG chunks (dry run, nothing deleted)
$ lm connector delete demo-invoices --force
deleted: demo-invoices
    • Without --force, lm asks you to type delete first.

    • If an entity (here invoice) is built on the table, it blocks the delete, before any question:

      $ lm connector delete demo-invoices --dry-run
Error: API error 409: table connector.t_invoices feeds entity invoice — remove the entity first (lm entity delete invoice)

    • The connectors lm source jdbc add made share the source's stored credential (<source>--credential). It goes with the last of them, and that one's statement names it: …, credential demo-src--credential, its run history and RAG chunks.

    • Re-apply the manifest and run it to start clean.

    The same holds for csv-file and kafka endpoints.

    • Another tenant is not a second connector. Each tenant's connector writes and reads only its own rows of connector.t_customers.
    • The rule holds across connector types: a csv-file connector named customers writes connector.t_customers too.

    When two connectors of a tenant already both write one hub table, both keep writing it:

    • lm connector delete on one removes only its rows; the table goes with the last of them. --dry-run counts those rows.
    • With different scopes, a user bound to only one of the métiers reads the table nowhere — not in lm data tables, not in either métier's chat. A user holding both scopes, or an unscoped one, still reads it.
    • To separate them, give the two connectors the same scopes, or move one to its own hub table with target: (above).

    Indexes on the hub table

    indexes: is declared per table for jdbc. A spec.target block, which CSV & files reads, gets an unknown key warning on a jdbc connector and is ignored.

    indexes:
  - { columns: [customer], unique: false }     # unique defaults to false

    Each entry is { columns: [non-empty strings], unique?: bool }; a malformed entry fails validation.

    Cursors — resume, restart, reset

    A cursor is stored per endpoint, after every chunk. An interrupted run resumes exactly where it stopped: no duplicates, no gaps.

    • mode: watermark resumes past the last watermark value and its row's key. Rows sharing one watermark value are neither lost nor read twice across chunks.
    • mode: full resumes past the last key.

    A run reads what the table held when it started

    • A row inserted while a run is in flight belongs to the next run. A run on a busy table still ends.
    • A row whose watermark is NULL is read by a first pass, never by a resume. To keep such rows current, give the column a value or read the table in mode: full.

    What restarts a table

    Changing mode, watermark_column or pk_columns — its columns or their order — restarts the table from the beginning. The hub log carries a WARN:

    demo.invoices: ignoring cursor persisted by another configuration (col='', pk=[invoice_id]; this reader writes col='updated_at', pk=[invoice_id]) — restarting from the beginning

    Rows the hub table already holds unchanged are skipped, so the table does not grow. IN and OUT count the re-read rows all the same — run 772a43f1 above.

    Restarting a table on purpose

    lm endpoint reset-cursor <connector>/<endpoint> drops the stored cursor; for jdbc the endpoint is the table name. It prints nothing; the next run's IN is the proof:

    $ lm endpoint reset-cursor demo-invoices/invoices
$ lm connector run demo-invoices

    Scheduling

    spec:
  schedule: "*/30 * * * *"   # cron, UTC
  window: "22:00-06:00"      # optional fence, UTC
    • schedule applies to the connector as a whole: all its tables ingest on the same trigger.
    • Both clocks are UTC, not the server's local zone.
    • window fences the schedule: a slot due outside it is skipped, never queued. A window may cross midnight.
    • The end is exclusive. A nightly 0 6 * * * needs a window ending later than 06:00, for instance 22:00-07:00.
    • A manual lm connector run ignores the window.
    • Re-applying without the key lifts it. An absent schedule unschedules; an absent window removes the fence.

    On a production database, a window is usually the DBA's condition for granting the SELECT account — see Sizing & load tests.

    Guided flow — lm source jdbc

    Four commands that create connectors without writing YAML. They need the lm_admin role. The password is never a flag:

    You are What happens
    at a keyboard Password for <user>: is prompted, and what you type is not shown
    piping, with --password-stdin the first line of stdin is the password
    piping, without the flag same, plus a warning on stderr naming the flag

    Use it to explore a base you do not know, and to stand up a table quickly. Write a manifest for rename, indexes, a view, a composite or undiscoverable key, or config kept in version control.

    test

    $ printf '%s\n' "$DB_PASSWORD" | lm source jdbc test --password-stdin --url jdbc:postgresql://postgres:5432/lumnik --user lumnik_readonly
OK       : true
Dialect  : postgres
Version  : 16.15 (Debian 16.15-1.pgdg12+2)
Latency  : 1 ms
Schemas  : connector, core, demo, ext, identity, information_schema, pg_catalog, platform, public, rag

    Schemas lists every schema of the database, granted or not.

    discover

    $ printf '%s\n' "$DB_PASSWORD" | lm source jdbc discover --password-stdin --url jdbc:postgresql://postgres:5432/lumnik --user lumnik_readonly --schema demo
SCHEMA     NAME                            ROWS  COLS PK                   WATERMARK       UNSUPPORTED
demo       audit_log                          1     3                      -               -

    Column / flag Meaning
    --schema defaults to public; an ERP in its own schema names it here
    ROWS the planner's estimate, -1 when the table was never analyzed
    PK empty: no primary key — that table needs a manifest or a view
    WATERMARK a suggestion: a column named updated_at, updated, modified_at or last_modified; else the first timestamp or date column; else a single numeric primary key — the trap named above (price_list suggests id)
    UNSUPPORTED the columns the dialect cannot read, as COLUMN TYPE (- when none). add refuses such a table by name; the interactive picker marks it [!]. Always - on PostgreSQL
    --include-views adds views to the listing
    --skip-pattern replaces the dialect's default exclusions (PostgreSQL: pg_*,information_schema*,t_*)
    --output json the whole descriptor, unsupportedColumns included

    add

    $ printf '%s\n' "$DB_PASSWORD" | lm source jdbc add --password-stdin demo-src --url jdbc:postgresql://postgres:5432/lumnik --user lumnik_readonly --schema demo --tables warehouses

    What it creates, per requested table:

    • one connector named <source-name>--<table>;
    • one encrypted credential per source, <source-name>--credential — the password never lands in a file;
    • mode: watermark when a watermark column was found, mode: full otherwise. There is no --mode.

    Flags:

    • --interactive opens a TUI table picker instead of --tables, pre-filled with the discovered suggestions.
    • --schedule-cron sets the schedule, in the 5-field form schedule: takes, e.g. */30 * * * *. It is checked like the manifest's: anything else is refused with invalid cron expression: … and nothing is created.

    What it refuses, by name and reason, before anything is created:

    $ printf '%s\n' "$DB_PASSWORD" | lm source jdbc add --password-stdin demo-src ... --tables audit_log
Error: API error 400: table demo.audit_log has no primary key — jdbc-generic pages by primary key; declare pk_columns in a manifest instead

Error: API error 400: table demo.nope not found among the base tables of that schema — check the schema and the connection user's SELECT grant; a view is declared in a manifest, not through the guided add
    • a table it cannot find in that schema, and a view;
    • a table without a primary key;
    • a table whose name is not a plain identifier;
    • mode: watermark with no column to watermark on.

    A table whose connector already exists is skipped, not re-created:

    $ printf '%s\n' "$DB_PASSWORD" | lm source jdbc add --password-stdin demo-src ... --tables warehouses
Created 0 connectors:
Skipped 1 (already exist):
  • demo-src--warehouses

    Oracle

    lumnik Pro. The Oracle provider ships in lumnik Pro with its JDBC driver — you drop no jar. The open edition has no Oracle provider: a manifest declaring dialect: oracle there is refused with JDBC dialect 'oracle' is not installed. Available: postgres.

    spec:
  connection:
    url: jdbc:oracle:thin:@//erp-db.acme.io:1521/ERP   # by service name
    user: ro_user
    password_env: ACME_DB_PASSWORD
    dialect: oracle                                    # optional, inferred from the url
  defaults:
    schema: ERP                                        # the OWNER, exactly as Oracle stores it
  source:
    tables:
      - name: ORDERS                                   # exactly as `lm source jdbc discover` prints it
        mode: watermark
        watermark_column: UPDATED_AT
        pk_columns: [ID]
        rename:
          ID: order_id                                 # optional: land a column under another name
    • Versions. Oracle 12c and later; tested on Oracle 23ai Free only. Oracle 11g is not supported.
    • Connect by service name: @//host:1521/SERVICE, @host:1521/SERVICE, or a full @(DESCRIPTION=…) descriptor (quote it in YAML). The SID form (@host:1521:SID) works on a non-multitenant database only; on a multitenant one it fails with ORA-01017. TCPS and wallets are not tested.
    • lm needs --schema. lm source jdbc discover and add default to --schema public; for Oracle pass the owner, e.g. --schema ERP, or the listing is empty.
    • Names are exact, never folded. Write schema, table and column names exactly as lm source jdbc discover lists them (ORDERS, not orders).
    • The hub columns keep that spelling — quoted upper-case ("ID", "UPDATED_AT"), next to the hub's lower-case system columns. Quote them in a query, or rename: them.
    • Empty string is NULL. Oracle stores '' as NULL; the hub receives NULL.
    • Index (watermark, key) on every Oracle table you page. Without it every page scans the whole table. A very large group of rows sharing one watermark value still pages more slowly.
    • Watermark ties and NULLs behave as on PostgreSQL — see A run reads what the table held when it started.
    Oracle type Lands as
    NUMBER, FLOAT, BINARY_FLOAT, BINARY_DOUBLE by the Column types table
    VARCHAR2, NVARCHAR2, CHAR, NCHAR, CLOB, NCLOB TEXT
    DATE, TIMESTAMP (no time zone) TIMESTAMPTZ, read in the connection's zone, UTC without one: DATE '2026-01-02' lands as 2026-01-02 00:00:00+00
    TIMESTAMP WITH [LOCAL] TIME ZONE TIMESTAMPTZ, the same instant — usable as a watermark
    BLOB, RAW, LONG, LONG RAW, XMLTYPE, BFILE, ROWID, object types refused: discover lists the column under UNSUPPORTED, add refuses the table by name

    Reading a view

    A view is how a table reaches the hub when the table itself cannot: no primary key, a reserved column name, a value too wide for the hub's numeric type, or more rows than the métier needs.

    # 50-view.yaml — read a VIEW instead of a table.
#
# A view is how a source-side table reaches the hub when the table itself cannot: no primary
# key to page on, a column name the hub reserves, a column too wide for the hub's numeric
# type, or simply more rows than the métier needs. jdbc-generic issues `SELECT *` — a view is
# a table as far as the read is concerned.
#
# The guided `lm source jdbc add` refuses views on purpose: a view has no primary key to
# discover, so `pk_columns` has to be declared, and that is what a manifest is for. The column
# named here must be unique and stable — it is what the reader pages on.
apiVersion: connectors.lumnik.io/v1
kind: Connector
metadata:
  name: demo-open-invoices
  connector_type: jdbc-generic
  scopes: [billing]

spec:
  connection:
    url: jdbc:postgresql://postgres:5432/lumnik
    user: lumnik_readonly
    password_env: LUMNIK_READONLY_DB_PASSWORD

  source:
    tables:
      # demo.v_open_invoices is created by data/demo-source.sql, with the tables.
      - name: v_open_invoices
        schema: demo
        mode: full
        pk_columns: [invoice_id]

    $ lm run list --connector demo-open-invoices
ID        CONNECTOR           ENDPOINT         STATUS     IN  OUT  SKIPPED  DEAD-LETTERS  STARTED           ENDED
22356ffd  demo-open-invoices  v_open_invoices  Completed  2   2    0        0             2026-10-19 01:42  2026-10-19 01:42

    The columns named in pk_columns must be unique together and stable — they are what the reader pages on.
