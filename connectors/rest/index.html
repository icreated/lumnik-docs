    REST

    Ingest any HTTP/JSON API: point at the base URL, declare the endpoints and how they page, apply. The rows land as typed columns plus the untouched JSON payload.
    Type rest-generic
    Protocol HTTP/JSON (+ the GraphQL and SOAP request shapes)
    Target the table each endpoint declares in target.table (ext.*)
    Schedulable cron
    Edition Open

    Every endpoint declares its own method; a source usually needs GET. The connector sends only the requests the manifest declares.

    Quickstart

    Every screen on this page reads a demo API that ships with the repo

    One Python file, no dependencies, 2 400 fictional ACME partners under ten path dialects. Start it in a terminal of its own, and put its three credentials in the hub's registry:

    python3 docs/connectors/rest/demo/acme-api.py
lm secret set ACME_BASIC_PW        # demo-pass
lm secret set ACME_BEARER_TOKEN    # demo-token
lm secret set ACME_API_KEY         # demo-key

    The manifests point at http://host.docker.internal:8099, because the hub runs in a container and localhost inside it is that container. What each dialect imitates, and which ones misbehave on purpose: The demo API.

    # 10-quickstart.yaml — one endpoint, a preset instead of a pagination block.
#
# `pagination: {kind: spring-page}` expands at apply time into the real strategy, read out of
# SpringPagePreset:
#   kind: page · page_param: page · size_param: size · start_page: 0
#   total_pages_path: $.totalPages · response_path: $.content
# Everything a Spring Data `Page` emits is covered, so `size` is the only field worth
# overriding — the strategy's own default is 50, which turns 2 400 partners into 48 requests.
#
# The password is never in this file. `password_env` names an entry the hub resolves at run
# time: the `lm secret` registry first, then its own environment.
#   lm secret set ACME_BASIC_PW        # the demo API answers to demo-user / demo-pass
#
# Expect: 2 400 rows in ext.acme_partners.

apiVersion: connectors.lumnik.io/v1
kind: Connector
metadata:
  name: acme-partners
  connector_type: rest-generic
  scopes: [billing]

spec:
  # The hub runs in Docker: `localhost` there is the hub's own container, not your machine.
  base_url: http://host.docker.internal:8099

  auth:
    kind: basic
    username: demo-user
    password_env: ACME_BASIC_PW   # BasicAuthProviderFactory has NO inline password field

  endpoints:
    - id: partners
      path: /spring/partners
      method: GET
      pagination: { kind: spring-page, size: 500 }
      target:
        kind: hybrid
        table: ext.acme_partners
        unique_key: "$.id"
        promote:
          - { name: name,         path: "$.name",         type: text }
          - { name: city,         path: "$.city",         type: text }
          - { name: credit_limit, path: "$.credit_limit", type: bigint }
          - { name: updated_at,   path: "$.updated_at",   type: timestamptz, transform: parse_iso8601 }

    $ lm validate -f docs/connectors/rest/demo/10-quickstart.yaml
✓ 10-quickstart.yaml — valid
$ lm apply -f docs/connectors/rest/demo/10-quickstart.yaml
{"name":"acme-partners","connectorId":"ff212939-378b-446c-adf5-d3356f85e9ff","endpointsApplied":1}

    Before running anything, send the first request a run would send:

    $ lm source rest test acme-partners
ENDPOINT  METHOD  STATUS  ITEMS  VERDICT
partners  GET     200     500    ok

    ITEMS is the number of records read from that one page (the manifest asks for 500). Nothing is written. Now run it:

    $ lm connector run acme-partners
run scheduled: 9deb9cb6-d9bc-427f-ba27-5af060647f19
$ lm run list --connector acme-partners
ID        CONNECTOR      ENDPOINT  STATUS     IN    OUT   SKIPPED  DEAD-LETTERS  STARTED           ENDED
9deb9cb6  acme-partners  partners  Completed  2400  2400  0        0             2026-10-19 01:39  2026-10-19 01:39

    STARTED / ENDED print in your terminal's time zone; schedule is evaluated in UTC.

lumnik->   FROM ext.acme_partners ORDER BY external_id LIMIT 4;

 1001        | Roulements Bruxelles 1001 | Bruxelles |          637 | 2026-01-01 00:01:00+00

(4 rows)
    • promote is a projection, not a filter. Every field the source returned is in data (JSONB); the promoted ones are also copied into typed columns.
    • unique_key makes a re-run safe. It becomes external_id, unique per tenant, and every write is an upsert — see Storage layout.
    • The password is never in the manifest. password_env names an lm secret entry (or, if none, an environment variable on the hub).

    The manifest

    spec:
  base_url: https://api.example.com
  auth: { kind: bearer, token_env: EXAMPLE_TOKEN }
  default_rate_limit: 100/s
  schedule: "0 6 * * *"          # optional cron, evaluated in UTC by the hub scheduler
  window: "22:00-06:00"          # optional fence, UTC, end exclusive, may cross midnight
  graphql_path: /graphql         # only for GraphQL endpoints; this is the default
  headers:
    - { name: X-Api-Version, value: "2026-01" }
  endpoints:
    - id: charges                # kebab-case, unique in the connector
      method: GET                # GET | POST | PUT | PATCH | DELETE
      path: /v1/charges
      pagination: { kind: stripe }
      incremental: { mode: full }          # optional, this is the default
      target:
        kind: hybrid
        table: ext.example_charges
        unique_key: $.id
        promote:
          - { name: amount, path: $.amount, type: bigint }
    • The path-shaped fields (cursor_path, response_path, unique_key, link_path, …) are JSONPath read against the response body: $.data[-1:].id is "the id of the last element of data".
    • A promote entry copies one value into a typed column. Values sent as text are read as the type says: "2026-10-01T08:01:00Z" as a timestamptz, "12" as a bigint, "true" as a boolean. A value that cannot be read leaves that column empty for the row, and the run counts it in cell_errors; the row is written and keeps the value in its payload.
    • A promote entry may also carry a transform: — the list is in Transformers, e.g. from_epoch for a number of seconds.
    • Without schedule, the connector runs only on lm connector run. window fences scheduled runs: a slot due outside it is skipped, never queued. A manual run ignores the window.

    An unknown key at the connector level of spec comes back as a warning; the manifest still applies:

    $ lm validate -f my-api.yaml
! my-api.yaml — 0 error(s), 1 warning(s)

  WARN     spec.headerz
          unknown key — ignored by the runtime
          → Remove it, or check the spelling

    One connector, one API

    One connector is one API, whatever number of endpoints it exposes. Two endpoints of the same API may page by different conventions:

    # 20-two-endpoints.yaml — one connector is one API, whatever number of endpoints it exposes.
#
# Both endpoints below read the same 2 400 partners from the same server, through two
# conventions that have nothing in common:
#
#   /v1/partners   opaque cursor  — ?starting_after=<id>, $.has_more says whether to continue
#   /drf/partners  follow a link  — $.next carries the whole next URL, until it is null
#
# Preset `stripe` expands to kind: cursor (cursor_param starting_after, cursor_path
# $.data[-1:].id, has_more_path $.has_more, response_path $.data); preset `drf-page` expands to
# kind: body-link (link_path $.next, response_path $.results). Neither sends a page-size
# parameter — see the page-size note in rest.md — so `page_size` rides in the DRF endpoint's
# own `path:`, which the request builder extends with `&`.
#
# The credential is declared once, at connector level, and both endpoints use it.
#
# Expect: 2 400 rows in each of the two tables.

apiVersion: connectors.lumnik.io/v1
kind: Connector
metadata:
  name: acme-saas
  connector_type: rest-generic
  scopes: [billing]

spec:
  base_url: http://host.docker.internal:8099

  auth:
    kind: bearer
    token_env: ACME_BEARER_TOKEN   # lm secret set ACME_BEARER_TOKEN   → demo-token

  endpoints:
    - id: cursor-partners
      path: /v1/partners?limit=500
      method: GET
      pagination: { kind: stripe }
      target:
        kind: hybrid
        table: ext.acme_cursor_partners
        unique_key: "$.id"
        promote:
          - { name: name, path: "$.name", type: text }
          - { name: city, path: "$.city", type: text }

    - id: link-partners
      path: /drf/partners?page_size=500
      method: GET
      pagination: { kind: drf-page }
      target:
        kind: hybrid
        table: ext.acme_link_partners
        unique_key: "$.id"
        promote:
          - { name: name, path: "$.name", type: text }
          - { name: city, path: "$.city", type: text }

    $ lm run list --connector acme-saas
ID        CONNECTOR  ENDPOINT         STATUS     IN    OUT   SKIPPED  DEAD-LETTERS  STARTED           ENDED
9d7a4883  acme-saas  link-partners    Completed  2400  2400  0        0             2026-10-19 01:40  2026-10-19 01:40
3531807d  acme-saas  cursor-partners  Completed  2400  2400  0        0             2026-10-19 01:40  2026-10-19 01:40

    The ledger records one run per endpoint. stripe and drf-page are two of the presets.

    Auth

    Kind Config
    bearer token_env: VAR_NAME (preferred), or token_value: "..." (dev only)
    basic username + password_env: VAR_NAME
    api-key in: header\|query, name, value_env: VAR_NAME
    oauth2 token_url, client_id, client_secret_env: VAR_NAME; optional scope, client_auth: basic\|post — below
    none no credentials (the default when auth: is omitted)

    Every auth *_env field names an lm secret entry first, then an environment variable / JVM system property of that name on the hub. Set the value before lm apply:

    lm secret set ACME_BASIC_PW     # prompts at the keyboard; what you type is not shown
    • basic and api-key have no inline field: the value comes from password_env / value_env, or not at all.
    • bearer: when both are set, token_env wins and token_value is ignored, even if nothing resolves under token_env. Declare one or the other.

    If the API writes your credential back into a response — an error that repeats the token it received, for instance — lumnik hides it as <redacted> before showing that response anywhere (lm source rest test, a failed run). The data you ingest is never rewritten: a token only looks like a credential where it can be recognised as one.

    A credential that does not resolve is named before any run:

    $ lm source rest test acme-badauth
ENDPOINT  METHOD  STATUS  ITEMS  VERDICT
partners  GET     -       0      Basic password unavailable (env=ACME_NOT_SET_PW)
Error: 1 of 1 enabled endpoint(s) did not answer with readable data

    OAuth2 client credentials

    A SaaS that hands out a client id and a secret, and wants a short-lived token on every call:

    auth:
  kind: oauth2
  token_url: https://auth.saas.example/oauth/token
  client_id: lumnik-orders
  client_secret_env: SAAS_CLIENT_SECRET
  scope: orders.read            # optional, space-separated
  client_auth: basic            # optional: basic (the default) or post
    • lumnik asks token_url for a token, keeps it as long as it is valid, and asks for a new one shortly before it expires.
    • If the API refuses a token during a run (for example after rotating its keys), lumnik asks for a new one once and repeats the request.
    • client_auth: basic works with almost every server; use post only if the server's documentation asks for it.

    With the secret set and the grant accepted, the pre-flight reads the first page:

    $ lm source rest test saas-orders
ENDPOINT  METHOD  STATUS  ITEMS  VERDICT
orders    GET     200     25     ok

    Once the SaaS has revoked that secret, the same command and the next run both say so:

    $ lm source rest test saas-orders
ENDPOINT  METHOD  STATUS  ITEMS  VERDICT
orders    GET     -       0      OAuth2 token refused by the authorization server: HTTP 401 invalid_client
Error: 1 of 1 enabled endpoint(s) did not answer with readable data

    What lm source rest test and a failed run say:

    Cause Verdict
    client_secret_env resolves to nothing OAuth2 client secret unavailable (env=SAAS_CLIENT_SECRET)
    The server refuses the grant OAuth2 token refused by the authorization server: HTTP 401 invalid_client
    token_url cannot be reached OAuth2 token request failed: host not resolved (UnknownHostException)
    The answer carries no token OAuth2 token response carries no access_token
    The token is under 8 characters OAuth2 access_token is shorter than 8 characters: too short to keep out of the source's responses

    invalid_client and similar codes come from the authorization server. The secret and the token are never shown.

    Pagination

    Every endpoint declares how the source hands back its next page. Most APIs follow a named convention, so the usual answer is one line:

    pagination: { kind: spring-page }        # Spring Data Page — seven fields under one word

    Eleven presets name the framework behind the API (Spring Data, Micronaut, Django REST, FastAPI, NestJS, JSON:API, Sequelize, Stripe). When none fits, write one of six strategies by hand: cursor, page, offset, link-header, body-link, relay.

    → Pagination — the catalogue, the fields of each strategy, where the cursor is injected, page size on the strategies that send none, and kind: custom.

    Request headers

    Connector-level only — spec.headers[] goes out on every request:

    spec:
  headers:
    - { name: X-Api-Version, value: "2026-01" }       # static
    - { name: X-Client-Id,   value_env: CLIENT_ID }   # from the environment
    • Each entry needs name + exactly one of value / value_env.
    • value_env reads the hub's OS environment, then a JVM system property. It does not read the lm secret registry.
    • A value_env that resolves to nothing drops the header, without a warning.
    • Headers are applied before auth — an auth-injected header wins a name clash.
    • Endpoint-level headers are refused:
    $ lm apply -f bad-headers.yaml
✗ bad-headers.yaml — 1 error(s), 0 warning(s)

  ERROR    spec.endpoints[0].headers
          per-endpoint headers are not supported in this release; declare headers at spec.headers
          → Move the headers block up to spec.headers (connector level)

Fix errors above before running 'lm apply -f bad-headers.yaml'.
Error: validation failed: 1 error(s)

    $ lm source rest test acme-witness

    Incremental sync

    incremental:
  mode: full              # re-fetch every page (default)
  # OR
  mode: watermark         # send the stored watermark as a query parameter,
  param: updated_since    #   e.g. ?updated_since=<watermark>
  watermark_path: $.updated_at   # new watermark = MAX of this JSONPath over the items read
  lookback: 10m           # optional — see "A change during a run" below

    mode: api_cursor behaves like full; lm validate warns about it.

    The watermark is stored per endpoint and survives runs.

    # 40-watermark.yaml — reading only what moved since last time.
#
# `mode: full` re-fetches every page on every run. `mode: watermark` sends the stored high-water
# mark as a query parameter on the first request of the run, and the API returns only what is
# newer:  GET /offset/partners?updated_since=2026-01-02T15:59:00Z&offset=0&limit=500
#
# The new mark is the MAX of `watermark_path` across the items actually read, compared as instants
# when they are instants (offsets may differ), as integers when they are integers.
#
# ── Why the first run is not the interesting one ─────────────────────────────────────────
# Run 1: nothing stored, so no parameter is sent — a full read, 2 400 rows.
# Run 2: the parameter goes out — the mark moved back by run 1's length plus a minute, so a row
#        changed while run 1 was paging is not left behind (#1397) — and only the rows stamped
#        in that window come back, the demo API filtering inclusively, as most APIs do. They
#        are re-upserted on their unique key, so they count as records_out and the table does
#        not grow. Run 2 reading 2 400 again would mean the watermark never persisted.
#
# ── The staged promotion, which is the subtle part ───────────────────────────────────────
# The mark is NOT advanced page by page. A crash mid-pagination would otherwise leave it past
# pages that were never fetched — silent, permanent data loss. The stored value keeps its
# pre-run reading throughout while a candidate carries the running MAX, and only the final
# chunk promotes it.
#
#   lm endpoint reset-cursor acme-incremental/partners     # the next run is full again
#
# A watermark is only as incremental as the column behind it: pointed at a column the source
# does not touch on update, it re-reads everything forever and reports it as new.
#
# Expect: run 1 = 2 400 in / 2 400 out. Run 2 = a handful in / out (the rows of the window), and
#         the table still 2 400.

apiVersion: connectors.lumnik.io/v1
kind: Connector
metadata:
  name: acme-incremental
  connector_type: rest-generic
  scopes: [billing]

spec:
  base_url: http://host.docker.internal:8099

  auth:
    kind: basic
    username: demo-user
    password_env: ACME_BASIC_PW

  endpoints:
    - id: partners
      path: /offset/partners
      method: GET
      pagination:
        kind: offset
        offset_param: offset
        limit_param: limit
        limit: 500
        response_path: "$.data"
        # No total_path here on purpose: an incremental endpoint returns a filtered slice, and
        # the source's unfiltered $.total is not the number it should be checked against.
      incremental:
        mode: watermark
        param: updated_since        # the query parameter the API filters on
        watermark_path: "$.updated_at"
      target:
        kind: hybrid
        table: ext.acme_incremental_partners
        unique_key: "$.id"
        promote:
          - { name: name,       path: "$.name",       type: text }
          - { name: updated_at, path: "$.updated_at", type: timestamptz, transform: parse_iso8601 }

    Run it twice. Run 1 has no mark, so it reads all 2 400 rows. Run 2 asks only for what changed since, with a small margin (below): a few rows come back and are updated in place. The table still holds 2 400 rows.

    • The mark advances only when the run completes, never page by page.
    • lm endpoint reset-cursor acme-incremental/partners clears it; the next run is a full read. The command prints nothing and exits 0.
    • Point watermark_path at a column the source updates on every change. Otherwise every run re-reads everything.
    • Date-times with a time zone are compared as moments, whole numbers as numbers (10 comes after 9); anything else as text.

    A change during a run

    An order that changes while a run is reading could be missed by the next run. To avoid it, each run asks from a little before the last mark: as far back as the previous run lasted, plus one minute. The few orders read twice are simply updated again.

    • lookback: 10m chooses that margin yourself; lookback: 0s turns it off.
    • It works when updated_at is a date and time with a time zone. With a change number or a date alone, the mark is sent as it is, and such a change can still be missed.

    Storage layout

    Each endpoint's table is created on the first run. This section is reference.

                                               Table "ext.acme_partners"
    Column    |           Type           | Collation | Nullable |                    Default                    
--------------+--------------------------+-----------+----------+-----------------------------------------------
 id           | bigint                   |           | not null | nextval('ext.acme_partners_id_seq'::regclass)
 tenant_id    | bigint                   |           | not null | 
 external_id  | text                     |           | not null | 
 name         | text                     |           |          | 
 city         | text                     |           |          | 
 credit_limit | bigint                   |           |          | 
 updated_at   | timestamp with time zone |           |          | 
 row_hash     | text                     |           |          | 
 data         | jsonb                    |           | not null | 
 indexed_at   | timestamp with time zone |           |          | now()
 connector_id | uuid                     |           | not null | 
 endpoint_id  | uuid                     |           | not null | 
Indexes:
    "acme_partners_pkey" PRIMARY KEY, btree (id)
    "acme_partners_tenant_id_external_id_key" UNIQUE CONSTRAINT, btree (tenant_id, external_id)
    "idx_acme_partners_data_gin" gin (data jsonb_path_ops)
Policies:
    POLICY "tenant_isolation"
      USING ((tenant_id = (NULLIF(current_setting('app.current_tenant'::text, true), ''::text))::bigint))
    Column Holds
    name, city, credit_limit, updated_at the promoted values
    external_id the unique_key; unique per tenant, so a re-run upserts instead of duplicating
    data the whole payload, GIN-indexed for JSONB path queries
    row_hash the payload's hash: a row whose payload and promoted values are unchanged is not rewritten
    tenant_id the row-level security policy keeps each tenant's rows invisible to the others

    A re-run rewrites only the rows that changed, yet OUT still counts every row read and SKIPPED stays 0. To check that nothing duplicated, count the table's rows.

    A new promote entry adds its column on the next run — see Add a typed column later.

    Deleting a REST connector deletes its data

    lm connector delete removes the connector's rows from its ext.* tables (a table goes with the last connector writing into it), and every RAG chunk it produced. To empty one endpoint's rows and keep the connector, see Empty one endpoint's rows.

    When the source misbehaves

    The engine retries what is worth retrying, refuses to read an error body as data, and — where the source publishes a count — checks the run against it.

    Retry, page cap, rate limit

    Guard Behaviour
    Retry fixed, not configurable: up to 5 attempts on HTTP 429, 500, 502, 503, 504, 408 and network errors; backoff 1s → 2s → 4s → … capped at 60s, ±10% jitter; a numeric Retry-After overrides the delay. Any other status: no retry
    Page cap 10 000 pages per endpoint per run
    Same request a next page whose request is identical to the one just sent ends the read: it would bring the same page back
    Rate limit default_rate_limit (default 100/s): count/window, window s, m or h with an optional integer (100/s, 100/5m, 1000/h). One bucket per connector, shared by all its endpoints — set it to the strictest endpoint's limit

    An outage fails the run

    /down/partners answers 500 to everything; /flaky/partners answers 429 then 503 before serving each page:

    # 60-source-down.yaml — what a run does when the source is simply down.
#
# `/down/partners` answers 500 to everything. The retry policy spends its five attempts, and
# then the run must FAIL: an outage that lands as a clean empty sync pages nobody, and the
# next run reads a table it believes to be current.
#
# The guard refuses a FINAL non-2xx, not a retried one — `/flaky/partners` below answers 429
# then 503 before serving each page, and its endpoint completes in full.
#
#   curl http://127.0.0.1:8099/admin/reset     # before re-running: the flaky counters persist
#
# Expect: `down` Failed with the upstream status in the message, `flaky` Completed with 2 400.

apiVersion: connectors.lumnik.io/v1
kind: Connector
metadata:

    A final non-2xx fails the run; it is never reported as an empty sync. A status that succeeds on retry does not — the flaky endpoint completes with all 2 400 rows.

    The pre-flight sends one request without retry, so a flaky source shows red there:

    $ lm source rest test acme-outage
ENDPOINT  METHOD  STATUS  ITEMS  VERDICT
flaky     GET     429     0      HTTP 429
down      GET     500     0      HTTP 500
Error: 2 of 2 enabled endpoint(s) did not answer with readable data

    Every enabled endpoint is tried; the command exits non-zero if any did not answer.

    The declared total — a witness on the count

    A run that loses rows can still end green. Where the source publishes its row count, total_path checks the run against it. /liar/partners serves 2 300 of its 2 400 partners and still declares "total": 2400:

    # 50-total-witness.yaml — the row count the source publishes, used as a witness.
#
# `/liar/partners` serves 2 300 of its 2 400 partners and still declares `"total": 2400`. The
# pagination ends the way a complete read ends — no error, no short page the strategy can see —
# so without `total_path` this run lands Completed with 2 300 rows and agrees with itself.
#
# With `total_path` pointed at that number, the run compares what it returned against what the
# source declared, and fails naming both figures. That comparison is exact and reads both ways,
# which is why it must point at a ROW count published by the source — never at a page count,
# never at an estimate.
#
# The second endpoint is the same shape against `/hdr/partners`, which answers 400 to any
# request without `X-Api-Version` — the declarative header at spec level below. Headers are
# connector-level only; a `headers:` key on an endpoint is refused at apply.
#
# Expect: `liar` FAILS on the mismatch, `hdr` completes with 2 400.

apiVersion: connectors.lumnik.io/v1
kind: Connector
metadata:
  name: acme-witness
  connector_type: rest-generic
  scopes: [billing]

spec:
  base_url: http://host.docker.internal:8099

  headers:
    - { name: X-Api-Version, value: "2026-01" }   # sent on EVERY request of this connector

  auth:
    kind: basic
    username: demo-user
    password_env: ACME_BASIC_PW

  endpoints:
    - id: incomplete
      path: /liar/partners
      method: GET
      pagination:
        kind: offset
        offset_param: offset
        limit_param: limit
        limit: 500
        response_path: "$.data"
        total_path: "$.total"       # the witness
      target:
        kind: hybrid
        table: ext.acme_witness_incomplete
        unique_key: "$.id"
        promote:
          - { name: name, path: "$.name", type: text }

    - id: versioned
      path: /hdr/partners
      method: GET
      pagination:
        kind: offset
        offset_param: offset
        limit_param: limit
        limit: 500
        response_path: "$.data"
        total_path: "$.total"
      target:
        kind: hybrid
        table: ext.acme_witness_versioned
        unique_key: "$.id"
        promote:
          - { name: name, path: "$.name", type: text }

    $ lm run list --connector acme-witness
ID        CONNECTOR     ENDPOINT    STATUS     IN    OUT   SKIPPED  DEAD-LETTERS  STARTED           ENDED
03b05ee0  acme-witness  versioned   Completed  2400  2400  0        0             2026-10-19 01:40  2026-10-19 01:40
a368b49d  acme-witness  incomplete  Failed     2000  2000  0        0             2026-10-19 01:40  2026-10-19 01:40

$ lm run get a368b49d
ID        CONNECTOR     ENDPOINT    STATUS  IN    OUT   SKIPPED  DEAD-LETTERS  STARTED           ENDED
a368b49d  acme-witness  incomplete  Failed  2000  2000  0        0             2026-10-19 01:40  2026-10-19 01:40
✖ run failed: Endpoint 'incomplete': the source declared 2400 rows but this run returned 2300 — refusing to report a partial extract as a complete one
    • 2300 is what pagination returned; IN 2000 is what had been written when the check fired.
    • A failed run is not rolled back: ext.acme_witness_incomplete keeps those 2 000 rows. The next successful run upserts over them.

    total_path is optional on every strategy; a soap endpoint ignores it. It also lets offset stop once every row is in. The drf-limit-offset and sequelize presets set it for you (total_path: $.count).

    The check is skipped when:

    • there is no total_path;
    • the endpoint is incremental (watermark) — it filters by design;
    • the total changes between pages — the source was written to during the read.

    Point total_path at an exact row count:

    • not a page count (total_pages_path) — a short page keeps the page count right while rows go missing;
    • not an estimate — the comparison is exact in both directions. Leave total_path unset instead.

    How to…

    Check a connector before running it

    lm source rest test <connector>

    Result: for each enabled endpoint, the hub sends the first request a run would send (same method, path, headers, auth and pagination) and reports what came back. Nothing is written.

    • 200 with 0 items: the response arrived but nothing matched response_path.
    • Disabled endpoints are skipped and counted on stderr.
    • -o json adds the URL called (host and path; the query string is not shown) and an excerpt of the body:
    $ lm endpoint disable acme-saas/link-partners
$ lm source rest test acme-saas -o json
note: skipped 1 disabled endpoint(s)
[
  {
    "endpoint": "cursor-partners",
    "method": "GET",
    "url": "http://host.docker.internal:8099/v1/partners",
    "status": 200,
    "ok": true,
    "items": 500,

  }
]
$ lm endpoint enable acme-saas/link-partners

    Draft an endpoint from a live path

    probe samples one path on an existing connector and prints the endpoint block that would ingest it. The base URL and credential come from the connector:

    $ lm source rest probe acme-partners --endpoint /spring/partners
# Auto-generated by RestProber (no LLM augmentation in v1)
- id: spring-partners
  method: GET
  path: /spring/partners
  pagination: { kind: page }
  target:
    kind: hybrid
    table: ext.acme_partners_spring_partners
    unique_key: $.id
    promote:
      - { name: id, path: $.id, type: bigint }
      - { name: name, path: $.name, type: text }
      - { name: city, path: $.city, type: text }
      - { name: country, path: $.country, type: text }
      - { name: credit_limit, path: $.credit_limit, type: bigint }
      - { name: updated_at, path: $.updated_at, type: text }

    Result: an endpoint fragment — paste it under spec.endpoints:, review it, then lm apply.

    • The pagination kind is a guess from the response envelope; an unknown envelope gives kind: unknown for you to fill in.
    • The promote list covers the scalar fields of the first record only.

    An upstream error is reported instead of a draft:

    $ lm source rest probe acme-partners --endpoint /open/nope
Error: API error 502: upstream returned HTTP 404 (permanent) — refusing to ingest its body as data: {"error": "unknown resource", "known": ["down", "drf", "flaky", "hdr", "liar", "link", "offset", "open", "spring", "v1"], "resource": "/open/nope"}

    A connector that is not rest-generic is refused by name.

    Generate a manifest from an OpenAPI spec

    lm source rest from-openapi \
    https://raw.githubusercontent.com/stripe/openapi/master/openapi/spec3.json \
    --name stripe --scope billing --output stripe.yaml

    Result: a manifest scaffold with the endpoints the spec declares — review auth, pagination and target before lm apply. A URL that holds no spec is refused:

    $ lm source rest from-openapi http://127.0.0.1:8099/spring/partners --name x --scope billing -o x.yaml
Error: API error 502: no OpenAPI spec could be read at http://127.0.0.1:8099/spring/partners — unreachable, not a spec, or not parseable

    Reset a stuck cursor

    lm endpoint reset-cursor <connector>/<endpoint>

    Result: the stored watermark is cleared and the next lm connector run is a full read. The command prints nothing.

    Empty one endpoint's rows

    lm endpoint purge deletes the rows one endpoint has landed and keeps the connector, its other endpoints and its run history. --dry-run only counts:

    $ lm endpoint purge acme-incremental/partners --dry-run
Would purge 2400 rows (dry run, nothing deleted)
$ lm endpoint purge acme-incremental/partners
Type 'purge' to delete 2400 rows: purge
Purged 2400 rows
$ lm endpoint purge acme-incremental/partners
Nothing to purge: this endpoint has no rows
    • Every rest-generic endpoint can be purged. A jdbc-generic, csv-file or kafka endpoint is refused — see Emptying one endpoint on its own.
    • --force skips the question.
    • Add lm endpoint reset-cursor to re-read the endpoint from scratch on the next run.
    • In lm ui, Del on :endpoints does the same, with the same count and question.

    Add a typed column later

    Add an entry to the endpoint's target.promote list in your copy of 10-quickstart.yaml (here acme-partners.yaml) and re-apply:

    promote:
  - { name: city,    path: $.city,    type: text }
  - { name: country, path: $.country, type: text }   # new column

    Result: lm apply changes nothing in the database; the next run adds the column and fills it as rows are read again.

    $ lm apply -f acme-partners.yaml

$ lm connector run acme-partners

$ lm run list --connector acme-partners

b9a1bf1a  acme-partners  partners  Completed  2400  2400  0        0             2026-10-19 07:25  2026-10-19 07:25
9af1c00d  acme-partners  partners  Completed  2400  2400  0        0             2026-10-19 07:25  2026-10-19 07:25

    A full endpoint fills every row on that run; a watermark endpoint fills only the rows that change, unless you lm endpoint reset-cursor first.

    Troubleshooting

    Symptom Cause Gesture
    Not sure the credential is valid — lm source rest test <connector> — one request per enabled endpoint, nothing written; an unresolved secret is named in VERDICT
    Run completed, IN is 0 the response arrived but nothing matched response_path lm source rest test <connector> shows 200 with 0 items; check response_path against the body
    Run failed on the source declared N rows total_path points at a number the run did not match check the source; if total_path points at a page count or an estimate, see The declared total
    429 Too Many Requests from the API default_rate_limit exceeds what the API tolerates lower it (100/s → 50/s); it is one bucket for the whole connector
    Sync stops picking up new rows the stored watermark is stale or points at a column the source does not touch lm endpoint reset-cursor <connector>/<endpoint> → the next run is a full read
    A run reads far more pages than expected cursor, body-link and link-header send no size parameter put the size in the endpoint's path: — see the page-size warning
    lm apply refused with an unknown transform a promote entry's transform: is not one of the supported values see Transformers
    Need to wipe an endpoint's rows — lm endpoint purge <connector>/<endpoint> — see Empty one endpoint's rows
