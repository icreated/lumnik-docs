    kind: SearchIndex — declare what Search may see

    A kind: SearchIndex manifest is an allowlist: the columns of one canonical entity that may leave PostgreSQL for an optional Search provider. No declaration, no indexing. Nothing is inferred from the data, and a column added to a source later never reaches the index on its own.
    Kind SearchIndex (apiVersion: search.lumnik.io/v1, strictly checked)
    Source one entity, never a raw connector.t_* table
    Who may see a hit whoever may read the entity: its scopes, resolved at query time
    Apply / delete lm_integrator
    List lm_user, filtered by the entity's scopes
    Provider needed? no — without one, a declaration is stored configuration and nothing more

    Quickstart

    apiVersion: search.lumnik.io/v1
kind: SearchIndex
metadata:
  name: customers
spec:
  entity: AcmeCustomer
  language: french
  fields:
    - name: name
      match: fuzzy
    - name: code
      match: exact
    - name: city
      match: text
      facet: true
    - name: segment
      facet: true

    curl -X POST "$LUMNIK_URL/api/search-indexes/apply" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/yaml" \
  --data-binary @docs/search/search-indexes/10-customers.yaml
# → {"name":"customers","entity":"AcmeCustomer","status":"valid"}

    Fields: searchable, returned, faceted

    Every declared field is returned with a hit. match also makes it searchable; facet: true also makes it a facet. So:

    • searchable ⊆ returnable and facet ⊆ returnable always hold. A field cannot be searched without being shown, so the index can never answer "does anyone earn 85 000?" about a column the caller cannot see.
    • A field without match is return-only: it rides along with the hit (a status, a date) but is never matched against.
    • At least one field must be searchable.
    apiVersion: search.lumnik.io/v1
kind: SearchIndex
metadata:
  name: orders
spec:
  entity: AcmeOrder
  fields:
    - name: order_no
      match: prefix
    - name: customer_name
      match: fuzzy
    - name: status
      facet: true
    - name: ordered_at
    match Meant for
    exact codes, identifiers, closed values
    text free text, analysed in spec.language
    fuzzy names with typos, accents and spelling variants
    prefix autocomplete, order numbers typed partially

    phonetic is refused as not supported yet: it returns once a provider proves it on French and German data.

    spec.language is one of simple (the default), english, french, german, italian, spanish, dutch, portuguese.

    What is refused, and why

    Refused Because
    spec.scope / spec.scopes scopes are inherited from the entity; a SearchIndex can never widen who sees its data
    spec.table / spec.source only a canonical entity has a stable identity and scopes; a raw table has neither
    a field that is not a canonical column of the entity the allowlist names canonical columns only (a source column name is not one)
    tenant_id, _entity_id, _conflicts, _resolution hub bookkeeping, never business data
    a metadata.name that is not a lower-case slug, or apply the name is used as written in DELETE /api/search-indexes/{name}
    an apply over an entity whose scopes you do not all hold 403 {"error":"scope not granted"} — holding one of two is escalation

    A re-apply of an existing name also needs every scope of the entity the name currently indexes, so nobody can take over a declaration they could not have written.

    Deleting — and the purge it leaves behind

    curl -X DELETE "$LUMNIK_URL/api/search-indexes/customers" -H "Authorization: Bearer $TOKEN"
# → 204

    A delete removes the declaration and records a purge obligation in the same transaction. The obligation outlives the declaration: documents already projected into a Search backend are purged even if the provider was down, absent, or installed only later. Re-applying the same name afterwards is a new declaration; it never cancels the pending purge.

    When the entity changes

    Entities are deployment-global. When one is re-applied without a column that a SearchIndex uses, every tenant's SearchIndex over it turns invalid, with the reason in the list:

    {"name":"customers","entity":"AcmeCustomer","language":"french",
 "status":"invalid","invalidReason":"spec.fields[2].name: 'city' is not a canonical column of entity 'AcmeCustomer'"}

    The entity apply itself is never refused because of Search. An invalid declaration takes no part in Search until it is re-applied successfully — restoring the column alone does not revalidate it.
